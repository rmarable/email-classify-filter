# Plan: ecf (email-classify-filter): consolidated v1 design, then write the docs (no code)

## Context

The repo holds an early personal-Gmail filer design (`LOCAL-EMAIL-PROCESSING.md`, `JEV-EMAIL-PROCESSING.md`) and a sketch. Over 2026-09-23..27 the operator and Claude redesigned it into a **team email-triage tool, delivered first as a single-user local v1**, with six numbered rounds of adversarial review, then AWS skill reviews, a Fable/Opus six-reviewer pass, a final Fable pass and several consistency checks:

- **Inputs:** watch a configured list of business mailboxes (e.g. `accounts-payable@`, `billing@`, `info@rodneymarable.com`).
- **Classify** each message against an operator-owned schema.
- **Decide actions:** server-side facts and rules first, then an actor model, then a server-side policy.
- **People** approve and answer in Slack.

This file is the **single consolidated statement of the agreed design**, including all accepted Review 4, 5 and 6 items and the later passes in the Review history. Superseded decisions are listed in the appendix only. The deliverables for this step are **documents only**; there is no code. Facts marked (rv) were verified by a reviewer's cited source, not re-checked by Claude.

## Scope: v1 = single-user local mode (operator decision 2026-09-26)

Sections below are tagged by where they land: **[v1]**, **[M1]**-**[M4]**, or **[later]**.

**In v1 [v1]**

## 1. Configurations, operating model and front ends [v1]

**Operating model (operator decision 2026-09-26; `/loop` removed from v1):**
- **Single-user** [v1]: ecf runs **only while the operator's computer is powered on and awake**. The local service runs the scheduled pre-check and the local-model checks (presets A and B, and preset C when its local fallback is enabled) (`ecf watch` runs the service in the foreground; `ecf service install` makes it the background unit) at each address's fetch interval (default 10 min in business hours, 30 min otherwise). Claude is used **on demand**: the operator opens Claude Code and runs `/ecf-review`.
- **Multi-user** [M2] (AWS mode only): **on demand for now.** Processing happens when a team member triggers it: `ecf check` (local models), `/ecf-review` in Claude Code, or a member choosing to run `ecf watch` while their computer is on. No always-on watcher is required or assumed.
- **Always-on operation** [M4] (including always-on all-Claude) is a roadmap item (§17): e.g. a mandated always-on team watcher host, the GPU server, or Bedrock for unattended Claude.

| | A: all-local | B: local classifier + Claude actor | C: all-Claude |
|---|---|---|---|
| Runs | `ecf watch` (at the fetch intervals while on) or `ecf check` | `ecf watch`/`ecf check` classify and apply rules; Claude actor items queue for `/ecf-review` | Everything waits for `/ecf-review` (on demand only) |
| Classifier, `standard` | Gemma 4 12B (Ollama) | Gemma 4 12B | `ecf:classifier` (Haiku family; full ID from `models.lock`; batched) |
| Classifier, `high` | Gemma 4 12B | Gemma 4 12B | `ecf:classifier-high` (Sonnet family; 1 message per spawn by default) |
| Actor, standard items | Gemma 4 12B | Sonnet, on demand | Sonnet, on demand |
| Actor, high-risk items | `local_high_risk` policy (§6) | Opus, on demand | Opus, on demand |
| Must be running | Computer on, Ollama, service | Computer on, Ollama, service; Claude Code only during review | Computer on, service (plus Ollama when the local fallback is enabled); Claude Code during review |
| Claude plan | none | the reviewer's own | the reviewer's own |

- **Claude review queue:** items needing the Claude actor (B) or everything (C) sit at `awaiting_claude` until someone runs `/ecf-review`, which works through the queue in an interactive Claude Code session and exits. **Local fallback when Claude isn't reviewed** (`claude_queue_timeout`, per address; default **off**; operator decision 2026-09-26, kept in v1 for **both B and C**; `ecf init`, `ecf watch` startup and `ecf doctor` remind you when it is off on a B or C address): when enabled, you set N hours yourself (no default); an item waiting longer than N goes to the local models: **B** → Gemma decides the action under `local_high_risk`; **C** → Gemma classifies and decides (preset A behavior) under `local_high_risk`.
  - **Its own gate:** whenever `claude_queue_timeout` is enabled, the service also runs the fallback models **in shadow** on each email (during shadow and assist, and **after go-live until the fallback's own gate passes**; operator decision 2026-09-26) (local only; no Claude usage); their proposals are reviewed like any other, and the fallback can't activate on an address until **its own gate** passes (same thresholds, the synthetic fraud cases, injection set 0, 0 unsafe payment/fraud proposals), bound to Gemma's manifest digest. Cost: extra Gemma work until that gate passes.
  - **If Ollama (Gemma) isn't available** where it is needed (presets A and B, or C with the fallback enabled; not installed, not running, or the pinned model missing): no local model runs, and nothing falls further; items keep waiting (at `new` in presets A and B, or `awaiting_claude` in C with the fallback enabled), the model-free pre-check and rules still run (fraud and regulator mail is still flagged), shadow runs of the fallback are skipped and don't count toward its gate, `[ecf-alert] System Error` ("local model unavailable") is sent once, `[ecf-alert] Resolved: System Error` when it returns, and processing resumes automatically. `ecf doctor` shows it. There is never a path where no model is consulted and actions still run beyond the model-free rules.
- **Validation:** config rejects combinations outside the three presets.
- **Pinned pair per address:** one configured (classifier, actor) pair plus, for B and C, the local fallback models used by `claude_queue_timeout`, each with its own gate; stored by the service; the service enforces high-risk ceilings from the pinned pair, not from what a client claims.
- **Claude usage:** only during `/ecf-review` and `/ecf-eval` runs; no idle usage. README: keep Claude's extra paid usage off, or capped.
- **Terms:** `/ecf-review` is an ordinary, operator-typed interactive command; `claude -p` and scheduled Claude runs are not used. Unattended Claude is the Bedrock roadmap item.
- **Not supported:** the claude.ai web app and desktop Chat tab for processing ([M3] they use the remote MCP, §9); desktop scheduled tasks; Windows (later).
- **B vs A:** the eval reports B's end-to-end result against A; B stays a preset regardless.


**Additions (§1) (Fable/Opus review 2026-09-27):** `ecf models install` pulls the pinned Ollama tag and verifies the digest (if the tag moved, it names the ecf release that moves the pin; pulling a specific digest is unverified, confirm in V1.3); the "local model unavailable" alert names it, and the daily summary shows "N items waiting for the local model since <time>". "Model and client processes never see them" is loosened: the CLI sees an app password only while you type it into the hidden prompt; tracebacks never use `show_locals`, and imaplib debug output is off. Whether other scripts using the same Python interpreter can read `keyring` Keychain items silently is unverified, confirm in V1.0.


**Final Fable pass (§1) (final Fable pass 2026-09-27):** `ecf models install` pulls the pinned tag, verifies the digest, then copies it to an ecf-owned tag (`ollama cp gemma4:12b ecf/gemma4-12b:<release>`), and ecf runs that tag, so an upstream `ollama pull` or tag move can't break checks; the "local model unavailable" alert distinguishes "Ollama not running (start the Ollama app)" from "model missing (`ecf models install`)". `ecf settings set --claude-model-override <id>` (step-up, Security Notice) lets reviews continue when a pinned Claude model retires before a release, dropping affected addresses to assist exactly as a release would. Work refused because telemetry shows a model other than the pinned ID or active override ends `/ecf-review` with "N refused (model X, expected Y)", sends one `System Error` and shows in `doctor`.

## 2. Architecture [M1 AWS mode; `ecf-mcp-remote` and the remote-MCP client are M3; v1 uses §10a]

```
Laptop (operator)                    AWS (base stack + app stack)                                  External
─────────────────                    ────────────────────────────                                  ────────
ecf CLI / ecf watch|check ─JWT─► API Gateway HTTP API ─► ecf-api ─┬─► DynamoDB / S3 / SSM
Claude Code + ecf MCP (stdio)                                (facts,    ├─► fetch jobs (async) ─► ecf-broker ──► IMAP/SMTP
Ollama (Gemma 4 12B)                                          rules,     └─► actions.fifo ─► ecf-broker (execute)
                                                              policy)
                                     Slack ──signed──► ecf-slack ─► ecf-api (DecisionService) ─► actions.fifo
                                     slack-out.fifo ─► ecf-slack (paced posts, DMs) ──► Slack
                                     EventBridge Scheduler ─► ecf-liveness ─► ecf-broker (pre-check fetch) ─► ecf-api ─► slack-out.fifo / alerts
                                     CloudWatch alarms ─► SNS ─► admin email (independent of Slack)
claude.ai / Claude apps ──OAuth──► API Gateway /mcp (no gateway authorizer) ─► ecf-mcp-remote (validates JWT itself)
Cognito (Essentials, TOTP): app clients CLI (PKCE loopback) · step-up (SRP only) · remote MCP (claude.ai callback)
```

- **`ecf-api`:** claim/lease/cursor; **computed facts, deterministic fraud triggers, rules and policy**; transitions; grants; config writes; stage/sensitivity/pause/outbound; admin ops; export/import staging; [M2] roles. JWT authorizer accepting only the CLI client's tokens with the required route scopes; handlers re-authorize the caller (the single admin in M1; [M2] against `people`).
- **`ecf-broker`:** the **only** holder of mailbox credentials (IMAP+SMTP; one app password per address). Fetches are **asynchronous** (operator decision 2026-09-27): `ecf-api` enqueues a fetch job and returns immediately, and `ecf-liveness` invokes the broker asynchronously per address (the HTTP API's 30 s limit can't hold a page fetch or a 64 MB message); broker timeout at least 6 minutes; also runs from `actions.fifo` (execute). No URL. The broker's asynchronous invocations (from `ecf-liveness` or `ecf-api`) get an **on-failure destination** (a standard SQS queue, alarmed on depth), so a fetch that fails after Lambda's built-in retries is never dropped silently (skill review 2026-09-27; retry behavior to confirm in the M1 dev stack; the execution role sends the records, documented).
- **Queues (SQS FIFO, `MessageGroupId = address_id`, DLQ each, `maxReceiveCount` = 5):** per the Lambda SQS guide (checked 2026-09-27): `maxReceiveCount` at least 5 so throttling alone doesn't dead-letter a message; each queue's **visibility timeout at least 6× its consumer's function timeout** (`actions.fifo` ≥ 36 minutes with the 6-minute broker; Lambda rejects an event source mapping whose function timeout exceeds the visibility timeout); FIFO batch size ≤ 10 (limit). Because a failed item would otherwise wait the full visibility timeout, the handler sets each failed message's visibility to the retry backoff (`ChangeMessageVisibility`) before reporting the partial-batch failure.
  - `actions.fifo`: carries **only a grant ID**; at execution the broker re-checks pause, stage, outbound and grant expiry. Partial-batch failures stop the rest of that address's group only: Powertools `SqsFifoPartialProcessor(skip_group_on_error=True)` with `FunctionResponseTypes=["ReportBatchItemFailures"]` on the event source mapping (by default it fails the rest of the whole batch, verified 2026-09-27, Powertools docs) (Fable/Opus review 2026-09-27); the handler marks an action `failed` after 3 attempts, before the queue's 5-receive DLQ limit. Redrive only via `ecf item requeue`.
  - `slack-out.fifo`: paces Slack posts (≤ 1/s/channel).
- **`ecf-slack`:** Slack interactivity: verify signature, 5-minute timestamp window, re-check `api_app_id`/`team_id`, dedupe payloads, acknowledge within 3 s, then submit the decision to `ecf-api`, whose `DecisionService` enqueues work. Consumes `slack-out.fifo`. No Events API.
- **`ecf-liveness`:** every **1 minute** (the scheduler tick; operator decision 2026-09-26; about $0.02-0.06/month): pre-check fetches that are due (§3a), audit flush to S3, approval expiry, grant voiding and `delayed → executing` transitions (performed through `ecf-api`), stale marking, "Needs you" refresh, hourly digests, daily summary, reminders, weekly model watch, refresh-expiry warnings. (In v1 the local service runs the same jobs on a 1-minute local timer.)
- **`ecf-mcp-remote`** [M3]: MCP over Streamable HTTP (JSON responses, no SSE; GET returns 405), Python MCP SDK v2 (verified; Mangum pattern from SDK issue #3121; `subscriptions/listen` handler removed per issue #3357; Lambda timeout 29 s). **No gateway authorizer on `/mcp`:** the Lambda validates the JWT itself (issuer, `client_id` = remote-MCP client, `token_use=access`, scope) and returns 401 with a `WWW-Authenticate` `resource_metadata` pointer. Serves RFC 9728 protected-resource metadata unauthenticated at both well-known paths (`resource` equals the connector URL; `authorization_servers[0]` is the Cognito issuer). Tools and rules in §9.
- **Capacity:** Lambda concurrency increase is an install prerequisite; reserved concurrency for `ecf-broker` and `ecf-slack` once the account quota leaves ≥ 100 unreserved (§10), and never below 5 per function (Lambda SQS guide, checked 2026-09-27); [M3] a concurrency cap on `ecf-mcp-remote`; throttling on unauthenticated routes.
- **Alarms and alert routing:** CloudWatch alarms (Lambda errors/throttles, DLQ depth, Slack post failures) and Budget notifications publish to an internal SNS topic (topic policy allows `budgets.amazonaws.com` and `cloudwatch.amazonaws.com`), consumed by a formatter in `ecf-liveness` (except `ecf-liveness`'s own error alarm and the heartbeat alarm, which publish to `ecf-alert-<install>-direct`, §10). The formatter republishes to an email topic (admin email subscriptions; Subject prefixed `[ecf-alert]`) and/or hands the alert (per-item fraud and regulatory alerts are the exception: `ecf-api` publishes them to the email topic itself, setting the `[ecf-alert]` subject and honoring `alerts.routes`) to `ecf-slack`, which posts to the summary channel via `slack-out.fifo`. Routing is configurable (§13). **Alarm definitions (observability skill review 2026-09-27):** every alarm sets `treatMissingData` explicitly; Lambda error alarms use the error **rate** (errors ÷ invocations, metric math), 60 s period, 2 of 3 datapoints, `notBreaching`; throttles likewise; DLQ alarms fire on `ApproximateNumberOfMessagesVisible > 0` (1 of 1, `notBreaching`), since any dead-lettered item needs a person; a **heartbeat alarm** fires when `ecf-liveness` has fewer than 1 invocation in 5 consecutive minutes (`breaching`), so a stopped scheduler is noticed (it drives the pre-check and every timer); duration alarms, if added, use p99, never Average. Alarm names start `ecf-alert-<install>-`. **Every Lambda log group is created explicitly in CDK with retention set to the smallest CloudWatch Logs retention value that is ≥ `log_retention_days`** (CloudWatch accepts only fixed values) (CDK's default leaves Lambda logs unexpiring); log lines carry no email content (structlog no-content processor, §14).
- **Laptops** run only the models, the classify/propose loop and the CLI/MCP. **No direct AWS or mailbox access**, except the operator's own deployer or admin credentials for `init`, `upgrade`, `budget set`, `retention set`, `destroy`, `billing activate-tags` and `doctor`'s read-only AWS checks.


**Final Fable pass (§2, M1) (final Fable pass 2026-09-27):** the broker executes only when invoked from `actions.fifo` (checked via the event source ARN), never on a direct invocation. Slack's 3 s acknowledgement and API Gateway's 30 s integration limit are documented (Slack interactivity docs; API Gateway HTTP API quotas).

## 3. Pipeline (every check, per address) [v1]

Component names below (`ecf-api`, broker, `actions.fifo`, `slack-out.fifo`, "server") refer to the local service and its SQLite job queues in v1 (§10a) and to the AWS components in M1. The model runner is the local service (Gemma, presets A/B) or Claude Code during `/ecf-review` (Claude, presets B/C).

1. **Take the check lease** (**3 minutes, renewed every 60 s while working**, operator decision 2026-09-26; **fencing token** required on every write; a crashed or sleeping holder blocks the address for at most 3 minutes). If another watcher holds it, skip the address.
2. **Start with what changed elsewhere** since the last check: approvals, answers, executions (already run by the service), and `prechecked` records still at `new`.
3. **Server fetches a page** via the broker since the server-owned cursor:
   - `UID SEARCH` plus batched `UID FETCH` of `RFC822.SIZE`, the envelope and `BODYSTRUCTURE`; then the **full raw message** via `BODY.PEEK[]` when `RFC822.SIZE` ≤ `max_message_bytes` (defaults **64 MB on `high` addresses, 16 MB on `standard`**, configurable per address; operator decision 2026-09-26), needed because DKIM signs the whole body including attachments. Messages over 16 MB (the `standard` default, a fixed threshold) are processed after the rest of the page, counted against the check's time budget and deferred to the next check if time runs out (never skipped). **Memory (reviewer recommendation confirmed by the operator; library behavior unverified, confirm in V1.1):** the IMAP fetch and `dkimpy` hold the whole message in memory, so peak use is roughly **4-6× the message size** (≈ 250-400 MB for a 64 MB message; unverified, measured in V1.1 with `tracemalloc`); oversized messages are processed one at a time across the whole service; the service logs the peak per message; the broker Lambda gets 1 GB (M1). IMAP library: `imapclient` (on stdlib `imaplib`; license verified, §14) unless the V1.1 real-service test shows it can't do partial and literal handling. Messages over the limit get headers and the first `max_scan_bytes_per_part` of each text part only; never sets `\Seen`;
   - page limit 30 messages or 20 s, whichever comes first (operator decision 2026-09-26);
   - `start_from: now` on first run; `ecf backfill --since` for history.
4. **Server computes facts** (§5 `computed`) and runs the **deterministic fraud triggers** (§6) over every decoded MIME part, after stripping hidden HTML text; scans each decoded text part up to **10 MB** (`max_scan_bytes_per_part`, configurable per address; operator decision 2026-09-26), measured and scanned after removing embedded base64 `data:` URIs from HTML (they carry no readable text); sets `content_unscanned` when a message exceeded `max_message_bytes`, a text part exceeded `max_scan_bytes_per_part`, or the item has attachments and payment keywords, a document attachment from a first-time sender, or any attachment on a `high` address; creates `MSG#` at `new`; advances the cursor; returns truncated text (about 1,500 characters for the classifier, 4,000 for the actor; text/plain preferred, HTML stripped) with a claim.
5. **The model runner classifies** against schema v1 (§5) and calls `record_classification`; the server validates strictly.
6. **Server runs rules** (first match wins; fraud guard first). The model's classification can raise risk; hide actions additionally need server corroboration (§6).
7. **The model runner's actor** runs only for items the server marks actor-needed; it proposes `{action, target, reason}` or `needs_clarification`.
8. **Server policy:** stage, sensitivity ceiling, action policy, `high_risk_route`, `outbound` switch. Auto actions get a grant and go to `actions.fifo`; items needing a person go to Slack via `slack-out.fifo`.
9. **Report:** Slack posts only for items needing a person (threads) plus the pinned "Needs you" message; auto actions roll into an **hourly** digest, which includes a per-address count of `content_unscanned` items (so oversized but harmless mail, such as newsletters, is visible); audit events written server-side. No idle posts.

- **Time budget:** `max_per_check` (default 6 minutes) bounds each check's IMAP and rules work; model work is bounded by the global model queue's budget (the same 6 minutes per scheduling round across all addresses); the rest waits for the next check.
- **One global model queue (operator decision 2026-09-27):** Ollama is one shared resource, so all local-model work (every address, the fallback shadow runs, evals) goes through **one queue with one global time budget** (evals take it exclusively and are exempt from that budget, §12); the per-address lease still serializes IMAP work. The model is unloaded only when the queue is idle (reference-counted), and Ollama runs one request at a time (`OLLAMA_NUM_PARALLEL=1`) so the stable prompt prefix may hit its cache (`prompt_eval_cached_count` is documented; the cache benefit is unverified, V1.3).
- **Throttling and battery (operator decision 2026-09-27):** each call's generation speed (`eval_count ÷ eval_duration`) is compared with a rolling median of recent calls; a drop of more than 30% (heat) pauses model work until the next interval. **On battery, model checks run at the off-hours interval (30 min)**; catch-up already requires AC power.
- **Large messages and small mail (operator decision 2026-09-27):** whether to fetch a large message is decided before the fetch from `RFC822.SIZE`, measured throughput and the remaining budget; full bodies are never batched into one FETCH; small mail is processed before deferred large mail, so it never waits behind it.
- **Catch-up mode** (operator decisions 2026-09-26; `catch_up: auto|off`, default `auto`): when a check ends with messages still waiting, the service starts the next check after a 30 s pause instead of waiting for the interval, until the backlog is empty or `catch_up_max_minutes` passes, then returns to the normal interval. **`catch_up_max_minutes` defaults by hardware: 30 on fanless laptops (MacBook Air, detected from the model identifier on macOS), 60 on everything else (including all Linux machines) except unknown Apple laptops (30) (no reliable fanless detection)** (configurable; to be checked against the planned load test on the Air). After hitting the cap, catch-up can't restart for **15 minutes** (`catch_up_cooldown_minutes`). If the check lease is busy when a round wants to start (pre-check or another model check), catch-up waits up to 60 s for it rather than ending. On laptops it runs only on AC power (battery state from `pmset` on macOS, `/sys/class/power_supply` on Linux) unless `catch_up_on_battery: true` (default `false`). Each round keeps the 6-minute budget and renews its lease every 60 s; the pre-check is unaffected. `ecf check --until-empty` does the same on demand.
- **Heartbeats** are kept for `status` only (shows which computers checked which addresses and when).
- **Folders:** INBOX only.
- **Local model loading:** kept loaded during a check (`keep_alive: "5m"` on each request) and unloaded **when the global model queue goes idle** with a final `keep_alive: 0` request (per-request semantics, reviewer recommendation confirmed by the operator 2026-09-26; documented: `keep_alive` default 5m, `0` unloads, per request, verified 2026-09-27, docs.ollama.com); `resident` (default `false`) set to `true` keeps it loaded on a computer that stays on (desktop or Mac mini).


**Additions (§3) (Fable/Opus review 2026-09-27):**
- **Digests:** one per address channel, posted only inside `business_hours` (off-hours auto actions roll into the first business-hour digest); its Pause pauses that address; fraud and regulatory escalations stay immediate. **Pause never stops the pre-check or fraud flagging.**
- **Model queue:** round-robin per address inside the global model queue, so catch-up on one address can't starve the others; the pre-check is unaffected. `OLLAMA_NUM_PARALLEL` and `OLLAMA_ORIGINS` are settings of your Ollama server, not ecf's: the README says how to set them and `doctor` reports them; every request uses one fixed option set (a reload on option change is unverified). That `OLLAMA_NUM_PARALLEL=1` improves prompt-cache hits is unverified.
- **Throttling:** heat is judged against a rolling median of recent calls, not one first-call sample. **Fanless detection:** a shipped lookup table of `hw.model` values; unknown Apple laptops default to 30 minutes.
- **Leases (v1):** renewed by a dedicated renewal thread that runs no jobs, plus a per-address `threading.Lock` for in-process exclusion; the fencing token is kept for M1 parity; the tick runs on monotonic deadlines, while due-ness uses wall-clock time (see Clocks below).
- **Crash-safe processing:** the service records "processing `<stable_id>`" before each message; after 2 crashes on the same message it quarantines it (`content_unscanned` plus escalate) and moves on, so one crafted email can't trip the crash-loop breaker and stop fraud checks for every address.
- **Large messages:** a SPEC option to parse headers with `BytesHeaderParser` and fetch text parts with `BODY.PEEK[n]` for the fact scan, so 64 MB messages don't build a full `email` tree. Held in memory as described in §3 step 3 (see the privacy note in §11).
- **Backlog visibility:** `status` and the "Caught up" line show the remaining backlog, an ETA from measured speed, and "waiting for AC power" when that is the reason.


**Final Fable pass (§3) (final Fable pass 2026-09-27):**
- **Clocks:** due-ness, lease expiry and approval TTLs use wall-clock time; the tick and the 10-minute send delay use the monotonic clock (which stops during sleep on macOS and Linux, documented); sleep is detected when wall-clock minus monotonic drift exceeds a threshold, and on wake every address's due time is re-evaluated at once.
- **Sleep and battery:** on AC power, model work holds an IOPM `PreventUserIdleSystemSleep` assertion (never on battery); the README says to keep the Mac plugged in during business hours; the daily summary shows "backlog grew by N today (on battery X h)".
- **Review volume:** shadow review posts are batched hourly inside `business_hours` like digests (escalations stay immediate); after the gate count (counted in **reviewed** items) review sampling drops to `review_sample_rate` (default 10%).
- **Backlog after a gap:** while a backlog exceeds 100 items, proposals post as batched review-style posts with "Approve all N reversible" per batch instead of one thread each; the "Caught up" digest links `ecf inbox`; the README states what a week away costs.
- **IMAP details:** `UID SEARCH UID <last+1>:*` can return the highest existing UID, so results are filtered to `uid > last_uid`; IMAPClient returns `BODY.PEEK[]` data under `b'BODY[]'`; IMAPClient is at 4.1.0 (verified 2026-09-27, PyPI).
- **Batched classification:** classifications record a `batch_id`; hide actions are never automatic when the batch contained any item with a fraud signal, `spam_or_phishing` or `fraud_risk ≥ low` (cross-item injection guard).
- DKIM signing the whole body (except with `l=`) is documented (RFC 6376).

## 3a. Scheduled pre-check (operator decision 2026-09-26) [v1 in the local service; M1 server-side in AWS]

Runs with no model and no client session. In v1 it runs in the local service while the computer is on; in M1 it runs in AWS, so it works even when every computer is closed.

- **Schedule:** per address, `mail_fetch_interval_workday` (default **10 min**) during business hours and `mail_fetch_interval_offhours` (default **30 min**) otherwise. Both configurable per install with per-address overrides; allowed range **5-120 min** (operator decision 2026-09-26). A 1-minute tick (the local timer in v1; `ecf-liveness` in M1) fetches each address whose interval has elapsed. The same intervals drive the local-model checks (presets A and B, and C's local fallback when enabled).
- **Business hours:** `business_hours` = days, start, end and IANA time zone per install (default **Mon-Fri 08:00-17:00, `America/New_York`** (US Eastern, observes daylight saving; operator decision 2026-09-26)), with per-address overrides. It also drives catch-up and any business-hours alert behavior (the M4 mail-delay alert).
- **What it does:** takes the check lease (fencing as usual; if a model check holds it, skip), fetches new mail through the broker (same limits: 30 messages or 20 s per page, full message up to the address's size limit), computes facts (DKIM/DMARC, sender history, Reply-To mismatch, bulk signal, `content_unscanned`), runs the deterministic fraud triggers and the regulator trigger (§6), creates the `MSG#` records, advances the cursor, and releases the lease.
- **Actions it may take (model-free rules only, within the address's stage):** a deterministic fraud trigger (§6; first-time sender + payment keyword without a second signal gets only `label(suspicious)`, `flag` and a digest section) → `label(suspicious)`, `flag`, `escalate` (rule 1 subset); a regulator trigger → `label(regulatory)`, `flag`, `escalate` (rule 2 subset); `payment keyword ∧ auth_result = none` → `label(unverified_sender)`, `flag` (all addresses, as rule 1a; the email alert fires on `high` addresses only). Nothing is hidden, moved, answered or sent. In shadow stage it posts only.
- **Hand-off:** records stay at `new` with `prechecked = true` (§4); the next model check (the local service's local-model checks, `ecf check`, or `/ecf-review`) picks them up for classification and the remaining rules. Model output can add risk but can't undo a pre-check escalation.
- **Escalation delivery:** fraud and regulatory hits: a Slack thread immediately (up to `escalations_per_hour` per address, default **20**, confirmed by the operator 2026-09-27; beyond that they roll into one "N more escalations" digest thread so a sustained flood is less likely to bury real fraud (the roll-up is ordered by severity); short bursts of more than 5 a minute are merged into one thread, §9) (operator decision 2026-09-27), plus email per the alert settings (`Possible Fraud Attempt`, `Regulatory Mail Notice`); unverified payment sender: the digest section, plus the hourly-batched `Unverified Payment Sender` email on `high` addresses (§13).
- **Cost (M1):** about 84 broker invocations per address per weekday (6/h × 9 business hours + 2/h × 15) and 48 per weekend day at the defaults; pennies. In v1 there is no cost.


**Additions (§3a) (Fable/Opus review 2026-09-27):** the escalation roll-up beyond `escalations_per_hour` is ordered by severity (a known sender with a bank change first), which makes burying real fraud less likely rather than impossible; bursts of more than 5 fraud **or regulatory** escalations a minute merge into one thread (§9).

- **Keys:** `pk = ADDR#<address_id>`.

  | `HEARTBEAT#<watcher>` | Watcher status (informational) |
  | `MSG#<stable_id>` | The message record |

- **Install-level items** (`pk = INSTALL`): config version pointers; [M2] `PEOPLE#<id>` (roles per address); [M3] `MCPCONN#<person>#<id>` (remote-MCP connections).
- **`stable_id`** (all providers): `sha256(address_id | normalized Message-ID | content_hash)`; `content_hash` = hash of the decoded text parts and raw attachment bytes from raw MIME, normalized for line endings, charset and trailing whitespace (size excluded); `hash_version` stored. Attachments' raw bytes are included in the hash from `hash_version` 1 (the raw message is already in memory for DKIM), so a replayed invoice with a swapped attachment is a new record; outside UIDVALIDITY recovery and rollback re-fetches, a `stable_id` collision at a new UID is recorded as a duplicate delivery, its `auth_result` compared, and the item flagged if it differs (it isn't re-actioned) (final Fable pass 2026-09-27). No Message-ID: `sha256(address_id | UIDVALIDITY | UID)`. A reused Message-ID with different content creates a second record and sets `duplicate_message_id`. Provider IDs live in the opaque `locator`.
- **Status** (`StrEnum`; the transition table is data, `Mapping[Status, frozenset[Status]]`, plus a guard table keyed by (from, to) for conditional edges such as `held → proposed` only when live, `clarified → proposed` only within the two-round cap, and the exits of `expired` and `awaiting_stepup`, which depend on the item's origin (clarification answer vs approval) (operator decision 2026-09-27); tested with Hypothesis; the only writer is `transition()` in `ecf_server`):
  - `new → classified → proposed → {auto → executing | awaiting_approval | needs_clarification | observed (shadow, terminal) | held (assist stage: action not allowed yet)}`; `held → proposed` (re-evaluated when the address goes live) `| resolved_manual`; held items appear as one batched digest line (not one "Needs you" entry each) and run only after the address goes live; you can still act on them by hand in your mail client (operator decision 2026-09-27); `new` records carry `prechecked = true` when the pre-check ran;
  - Claude queue: `new → awaiting_claude → classified` (preset C) and `classified → awaiting_claude → proposed` (preset B); with `claude_queue_timeout` set and the fallback gate passed, `awaiting_claude → proposed` via Gemma (B), or `awaiting_claude → classified → proposed` via Gemma (C);
  - `awaiting_approval → {approved → executing | rejected | awaiting_stepup → {approved | expired} | expired}` (step-up requests expire with the same approval TTL); single-approver sends on `high` addresses: `approved → delayed (10 min) → executing | cancelled`;
  - `expired → needs_clarification` for an expired step-up answer; otherwise `expired → awaiting_approval` (the person decides again; after a second expiry the item is listed only in the daily summary, not re-posted) `| resolved_manual`; any open item whose email you've already moved, archived or deleted in your mail client is closed automatically as `resolved_by_mailbox` (checked each check) (operator decision 2026-09-27);
  - `needs_clarification → clarified → proposed` (at most 2 rounds, then `needs_human`; answers on payment or fraud items pass through `awaiting_stepup → clarified | expired`, and an expired answer returns to `needs_clarification`); `needs_human → proposed | resolved_manual`; [M3] remote-MCP answers: `needs_clarification → answer_proposed → clarified` (confirmed in Slack) `| needs_clarification` (rejected);
  - `executing → executed | failed` (3 attempts, backoff); unknown send outcome → if the per-address probe found that the provider **saves sent mail itself**, the broker searches `\Sent` for the pre-generated Message-ID and settles `executed` or `failed`; otherwise (ecf appends its own copy only after a confirmed send) → `failed_unknown` (escalated); `failed | failed_unknown | executing` (stuck) `→ executing` via `ecf item requeue` (a person decides; the broker reconciles against the mailbox first);
  - `executed → undoing → undone | undo_failed` (reversible actions only);
  - any open status → `resolved_manual` via `ecf item resolve --reason` or Slack **Dismiss** (non-payment, non-fraud items);
  - ✅ Correct records `review = correct`; Fix (✏️) records `human_correction`; it returns the item to `proposed` when the decision changes, except on `observed` (shadow) items, where it only records the correction for the go-live gate.
  - Attributes: `decision_source` (`rule`, `actor`, `human`), `proposed_by`, `suppressed_action`, `review`, `pinned_models` (model IDs and Ollama digest used), `prechecked`, `stale`.
- **Grants** bind `stable_id`, `content_hash`, the canonical action hash (action, target, template, resolved recipient), the executing principal and an expiry. Single-use (conditional write; in M1 performed by `ecf-api`, the only writer of grants). The broker re-resolves the locator and verifies `content_hash` before acting.
- **Leases:** claims carry `claim_expires` and the fencing token; stale tokens are rejected. `executing` is reconciled against mailbox state before any retry.
- **Retention:** sender history (`SENDER#`), send and thread history (`SENT#`, `THREAD#`), gate history (`GATE`) and eval labels are **exempt** from retention pruning, so first-time-sender status and loop prevention survive (operator decision 2026-09-27); terminal statuses are deleted after `log_retention_days` (default 90, range 1-3650; stored in local config and enforced by a daily local job in v1; SSM plus DynamoDB TTL and S3 lifecycle in M1). Pending approvals expire (operator decision 2026-09-26): **sends** (`reply_template`, `forward_internal`) after `approval_ttl_days_send` (**4 days**, so a long weekend doesn't lapse them) and **everything else** after `approval_ttl_days` (**14 days**); both configurable per address. On expiry nothing executes, the grant is voided, and the item returns to "Needs you" as "expired, decide again" (an expired step-up answer has no grant and returns to `needs_clarification` instead). Open records are **never auto-closed**, except as `resolved_by_mailbox` when you've already moved, archived or deleted the email (above): after `stale_item_days` (30, operator decision 2026-09-26) an open record is marked `stale = true` (attribute, not a status), shown at the top of "Needs you" and `ecf inbox`, and listed in a daily summary until a person resolves it (stale `held`, `new` and `awaiting_claude` items appear as one count line) (`ecf item resolve`). Open records carry no TTL.
- **Index of open items** per address (SQLite partial index in v1; sparse GSI in M1), feeding "Needs you" and `ecf inbox`.
- **Every item carries `schema_version`** for migrations.


**Additions (§4) (Fable/Opus review 2026-09-27):**
- **Statuses:** SPEC lists every status as open or terminal. Terminal: `observed`, `executed`, `undone`, `rejected`, `cancelled`, `resolved_manual`, `resolved_by_mailbox`. Open: `new`, `held`, `proposed`, `awaiting_*`, `approved`, `delayed`, `executing`, `failed`, `failed_unknown`, `expired`, `needs_clarification`, `needs_human`, `classified`, `clarified`, `undoing`, [M3] `answer_proposed`, and `undo_failed`; a terminal `executed` item can still be undone. `auto` is a decision, not a status. Edges: `undoing → undo_failed`; `needs_clarification → awaiting_stepup`, then `awaiting_stepup → clarified` or `awaiting_stepup → expired → needs_clarification`, for answers on payment or fraud items (expiring with the approval TTL; sender confirmations use a step-up nonce with no item status change); `undone → proposed` (Fix only); `needs_clarification → needs_human`; Fix from `awaiting_approval`, `held` and (via undo) `executed`; sends run `awaiting_approval → awaiting_stepup → approved → executing`, with `approved → delayed → executing` on `high` addresses only. An `expiry_count` attribute drives "after a second expiry" for both approvals and step-up answers: after a second expired answer the item goes to `needs_human`; an expired answer counts as one of the two clarification rounds. Pre-check actions run from `new` with a grant and an audit entry and no status change. Guard examples: `held → proposed` only when live; `clarified → proposed` only within the two-round cap; `awaiting_stepup → clarified` for answers vs `→ approved` for approvals; `expired → needs_clarification` for answers vs `→ awaiting_approval` for approvals. Tested with a Hypothesis `RuleBasedStateMachine` driving `transition()` against SQLite.
- **Undo:** archive, move and junk are undone by moving back to INBOX (UID re-resolved by Message-ID); label and flag by removing the keyword or flag; mark_read by removing `\Seen`; drafts by deleting them; available until retention removes the item.
- **UIDVALIDITY:** messages without a Message-ID are matched by `content_hash` plus INTERNALDATE during recovery; a mailbox reset is informational (no input needed); open locators are re-resolved by Message-ID search.
- **Stale items:** `held`, `new` and `awaiting_claude` items past 30 days show as one count line, not individually. `ecf stage set live` prints held counts by age and offers to resolve held items older than N days (default 7) as `resolved_manual`.
- **Short IDs:** a unique hex prefix of at least 8 characters is accepted wherever `<id>` is.
- **Grants:** the hash also covers template text and draft text. Requeuing a send voids its grant and needs a new approval plus step-up. The 10-minute send delay counts only time the service is awake; on wake it re-announces "sending in 10 minutes".
- **Rollback:** the sent, threads, senders and gate tables survive `ecf upgrade --to <previous>`, and the cursors are rewound so mail since the upgrade is fetched again (§10a).


**Final Fable pass (§4) (final Fable pass 2026-09-27):** on approval expiry the Slack card is edited in place with a fresh grant and the "expired, decide again" label (`expiry_count` drives the second-expiry rule). Job claim: the `RETURNING` cursor is stepped (`fetchone()`), and per-address FIFO adds `AND NOT EXISTS (an in-flight job for the same address)` to the subquery; all leases are cleared at service start (one process in v1). `ecf approve --pending` issues one batch nonce over the hash of the listed grant IDs. Keywords carry the install ID (`$ecf_<install>_<t>`), so this install's own keywords without a local record (after a restore) are adopted silently and only foreign IDs pause an address.

- **ecf's own DKIM/DMARC verification (primary, all providers; operator decision 2026-09-26):** at fetch time (usually soon after arrival; in v1, mail that waited while the computer was off may be verified days later, after a sender rotated keys, which yields `none`, never `pass`; the eval set includes this backlog case), the service verifies every DKIM signature on the raw message (`dkimpy` + `dnspython`), looks up the From domain's DMARC record, and applies relaxed/strict alignment; the DMARC policy record is found per **RFC 9989** (May 2026; obsoletes RFC 7489 and RFC 9091), using its DNS Tree Walk instead of the Public Suffix List, with `p=`/`sp=`/`np=`/`t=` (`pct` removed) (verified 2026-09-27, datatracker.ietf.org/doc/rfc9989) (Fable/Opus review 2026-09-27); no PSL library is needed. `dkimpy` verifies signatures only; ecf implements the DMARC steps (record lookup, `p=`/`sp=`/`np=`/`t=`, alignment, result) itself, specified in SPEC. An aligned valid DKIM signature is a DMARC pass without trusting any provider header, **with these strictness rules (operator decision 2026-09-27):** a signature with a body-length tag (`l=`) counts as unverified; the signature must cover From, Subject, Date, To and Reply-To (when present) and Content-Type, MIME-Version and Content-Transfer-Encoding (when present; added (operator decision 2026-09-27) so a signed message can't be replayed with altered MIME headers; senders that don't sign them get `auth_result = none`), and extra unsigned copies of those headers make it unverified; a message with more than one From header is `fail` and a fraud trigger. **DNS limit (SPEC owns; SECURITY.md summarizes) (operator decision 2026-09-27):** key lookups use ordinary DNS, which can be forged on a hostile network; DNS results are cached in SQLite across checks (respecting TTLs but capped at the address's check interval, with negative caching; encrypted DNS (DoH) to a resolver you choose is an opt-in setting, since it shows every sender domain to that resolver) (operator decision 2026-09-27), looked up in parallel with a 1.5 s timeout and 3 s lifetime, within a per-check DNS budget after which results are `none`. Limits: SPF can't be evaluated after delivery, so SPF-only senders stay `none`; forwarded and mailing-list mail often breaks DKIM (ARC evaluation is a roadmap item); a DNS failure yields `none`, never `pass`; messages over `max_message_bytes` (64 MB on `high`, 16 MB on `standard`) aren't verified and yield `none` (so a large payment email on a `high` address lands in the unverified-sender section, flagged and never hidden). Results (`dkim_domains_valid`, `dmarc_policy`, `alignment`) are stored on the record and shown on approval cards. In dev, OpenDKIM signs synthetic senders so the check is tested end to end.

\* **Hide corroboration:** a hide action runs automatically only when the service corroborates it: `bulk_signal`, or a human-confirmed category for this sender (`SENDER#`) **counted only when the current message's `auth_result = pass`** (reviewer recommendation confirmed by the operator 2026-09-26; stops a spoofed From from borrowing a confirmed sender's trust). - **Outbound switch:** `forward_internal` and `reply_template` (the sends) require `OUTBOUND = on` (default **off**); `draft_reply` is not gated by it, because a draft never sends, but always needs approval (operator decision 2026-09-26). - **Outbound guardrails:**
  - reply only if `auth_result = pass` and there is a single From mailbox; never to a differing Reply-To;
  - no send for `bulk_signal`, `content_unscanned`, fraud-guard or fraud-signal items;
  - one template reply per thread;
  - **send circuit breaker** per address (operator decision 2026-09-26): `max_sends_per_hour` (default 25) and `max_sends_per_day` (default 250), configurable per address (`ecf address set <address> --max-sends-per-hour N --max-sends-per-day N`, admin + step-up, announced). Purpose: stop mail loops, spam amplification via forged inbound, a compromised approver, or a sending bug. When tripped: outbound for that address pauses, pending sends stay queued (never dropped), `[ecf-alert] Operator Input Needed` is sent, and `ecf outbound resume <address>` (step-up) restarts it;
  - a pre-generated Message-ID and content hash recorded in `SENT#` before sending; an inbound message is skipped as ecf's own **only** if its Message-ID is in `SENT#`, it passes DMARC from the install's own address, and its `content_hash` matches;
  - sent copies appended to `\Sent`.
- **Deterministic fraud triggers** (computed by the service, every decoded MIME part, hidden HTML text stripped):
  - bank-detail keywords (bank, IBAN, routing, wire, account number) **together with** a first-time sender, change wording (e.g. "new account", "updated bank details", "change of remittance"), or `reply_to_mismatch` (operator decision 2026-09-26; bank keywords alone do not trigger, so a known vendor's normal invoice doesn't alarm);
  - a first-time sender plus a payment keyword **together with a second signal** (bank or change wording, `reply_to_mismatch`, `auth_result = fail`, `recipient_mismatch`, or a lookalike domain; `auth_result = none` is not a second signal and stays in the unverified-payment-sender digest, rule 1a, operator decision 2026-09-27); on its own, first-time sender + payment keyword only labels and flags the item and lists it in a digest section (no escalation, no email) (operator decision 2026-09-27);
  - lookalike or homoglyph domains versus `org_domains` and known vendors;
  - DMARC fail on a payment item;
  - `duplicate_message_id`;
  - an `X-ECF-Install` header on a message not skipped as ecf's own (except a mismatched `X-ECF-Install` on a message from this install's own address with `auth_result = pass`, which pauses the address as a possible second install, §13).

- **Starter rules** (structured YAML AST with a grammar defined in SPEC; represented as a Pydantic discriminated union of operators (`eq`, `in`, `gte`, `and`, `or`, `not`) compiled to predicates; ordinal fields keep their level order so `priority ≥ high` works (operator decision 2026-09-27); fields, operators, actions, "then continue", and the compiled form; validated at load; **no eval**; first match wins unless a rule says "then continue"; run by the service):
  1. **Fraud guard:** any of `fraud_risk ∈ {medium, high}`, `category = vendor_change_request`, `sender_type = staff ∧ sender_origin = external`, `payment_related ∧ auth_result = fail`, or a deterministic fraud trigger (not the regulator trigger, and not first-time sender + payment keyword without a second signal, which gets `label(suspicious)`, `flag` and a digest section) → `label(suspicious)`, `flag`, `escalate`.   1a. **Unverified payment sender** (all addresses; operator decision 2026-09-26): `payment_related ∧ auth_result = none` → `label(unverified_sender)`, `flag`; no actor, never hidden; listed in a digest section, not a thread each; the email alert fires on `high` addresses only (§13).
  2. **Regulatory** (category or regulator trigger) → label, flag, escalate.
  3. **Bug report** → label; flag if `priority ≥ high`; escalate if urgent; **then continue to the actor if `requires_reply`**.
  4. **Invoice** → label; flag if `deadline_mentioned`; leave; **then continue to the actor if `requires_reply`** (e.g. a "received your invoice" template).
  5. **Payment confirmation / remittance** → label; **then continue to the actor if `requires_reply`** (rules 3-5 continuation: operator decision 2026-09-26; high-risk items still go to Opus or `local_high_risk`).
  6. **Spam or phishing** → label, junk (hide corroboration applies).
  7. **Marketing ∧ ¬requires_action** → label, archive (hide corroboration applies).
  8. **Notification ∧ automated ∧ ¬requires_action** → label, mark_read, archive (hide corroboration applies).
  9. **requires_reply** → label(category), flag, **then continue to the actor** (operator decision 2026-09-26), so it can propose a draft or template reply.
  10. **Otherwise** → actor.

- **Reply-To mismatch on payment items is a second signal only:** alone it flags the item and lists it in the digest; with another signal (bank or change wording, `auth_result = fail`, lookalike domain, `recipient_mismatch`) it escalates. `ecf sender set-reply-to <sender> <domain>` (step-up) records a sender's expected Reply-To domain on `SENDER#`, and a match isn't a mismatch.
- A mismatched `X-ECF-Install` from this install's own address pauses the address only when `auth_result = pass` for that address and the message is otherwise ecf-shaped; otherwise it is just the fraud trigger (so anyone forging the header can't pause the mailbox) (final Fable pass 2026-09-27).
- The webmail search link percent-encodes the Message-ID and fixes the host; YAML is always loaded with `YAML(typ="safe")`, including import bundles; an optional per-address `label_folder` copies `suspicious` and `regulatory` items to a visible folder on providers whose webmail hides keywords (final Fable pass 2026-09-27).

## 7. People, stages, sensitivity, approvals and outbound [v1 single-approver; items marked [M1]/[M2]/[M3] are later]

- **[M2] Roles per address:** `approver` (approve/reject, answer, review), `reviewer` (answer, review, Fix/Correct), `observer` (read only). Admin is install-level. `ecf people add` previews the effect (e.g. "billing@ will need two approvers") and asks to confirm.
- **Approval mode** per address: v1 is always **single-approver**. [M2] **multi-approver** (≥ 2 approvers); any change that lowers the count needs step-up.
- **Stages** (`STAGE`, enforced by the service; shown as "Watching only / Labels only / Full"):
  - **shadow:** decide and post, change nothing;
  - **assist:** only label, flag, escalate and leave execute; other actions become `held` items, listed as one digest line and run after go-live (§4);

- **Review:** each item card has ✅ **Correct** and ✏️ **Fix**; each review post has **All others correct** (covers items not Fixed). `ecf stage status` shows progress ("73/100 reviewed, 91% accurate, 27 to go").

  - **standard:** ≥ 100 reviewed items, category accuracy ≥ 85%, 0 fraud-guard misses;
  - **high:** ≥ 200 reviewed and ≥ 90%;

- **[M1] Moving to AWS later (local → AWS, then single- or multi-user):** a first-class, documented path, `ecf migrate`, built on export/import. Steps:
  1. **Plan:** `ecf migrate plan --to aws` checks prerequisites (AWS account and admin credentials, region, Slack admin access, the authenticator app for Cognito), lists what moves, what must be re-entered, and the expected downtime (minutes), and changes nothing.
  2. **Deploy AWS:** `ecf init --mode aws --migrating` deploys the stacks and creates you as the Cognito admin (TOTP enrollment). No addresses yet; nothing touches the mailboxes.
  3. **Cut over:** `ecf migrate run`:
     - pauses every address and stops the local service (no mail is processed during the cutover);
     - takes a final export (records, cursors, config and versions, roles, audit, eval labels, go-live history, open items);
     - imports it into AWS as a **migration import**: same person, proven by local OS authentication plus a Cognito step-up, so the import limits in §13 (`ecf import`) apply with two relaxations: you keep approval authority, and each address's stage is restored when you resume it (below);
     - moves mailbox app passwords from the OS secret store to Secrets Manager directly (write-only via `ecf-api`; nothing to retype; you confirm each address);
     - switches Slack from Socket Mode to the AWS request URL on the **same app** (manifest update), so channels, history and route IDs are kept; the app-level token is revoked (to verify in group 2; fallback: re-install and re-bind existing channels).

  5. **Grow to multi-user (optional, any time later):** `ecf people add` for teammates. `people add` previews the effect: an address switches from single-approver to multi-approver rules once it has two approvers. Slack-only teammates need no Cognito account.
  6. **Rollback window:** the local data and secret-store entries are kept, service disabled, for 14 days. Before AWS processes any mail, `ecf migrate rollback` re-enables local mode unchanged. After AWS has processed mail, rollback is `ecf export` from AWS then `ecf import` into local mode (single person only).
  7. **Finish:** `ecf migrate finalize` (after the window, or on demand, with step-up) deletes the local data and secret-store entries and prints what else to remove (local service, launchd/systemd unit).

**Additions (§10a) (Fable/Opus review 2026-09-27):**
- **Process model:** uvicorn's `serve()` runs in a non-main thread; the main thread owns signals and sets the stop event, then `should_exit`, then joins the other threads in order with timeouts; `ExitTimeOut` (launchd; its default is system-defined, so ecf sets it explicitly, verified 2026-09-27, launchd.plist(5)) and `TimeoutStopSec` (systemd) are set; an in-flight step is finished or abandoned, and `executing` reconciliation covers it; both stop timeouts exceed the longest write transaction plus the 20 s page fetch. An in-process watchdog exits non-zero (so launchd/systemd restart it) and notifies you if no timer tick happens for 5 minutes while awake; `status` and `doctor` show the last tick.
- **SQLite:** `sqlite3.connect(path, autocommit=True, timeout=5.0)` (Python 3.12+; `isolation_level` is ignored once the default changes; the connection factory sets `synchronous`, `busy_timeout` and `foreign_keys` on every connection, while WAL persists in the file) (final Fable pass 2026-09-27) with a `write_tx` helper issuing `BEGIN IMMEDIATE`/`COMMIT`/`ROLLBACK`; `busy_timeout` 5000 ms; jobs claimed with `UPDATE … WHERE id = (SELECT … ORDER BY … LIMIT 1) RETURNING …`; workers wait with `cond.wait(timeout=next_due - now)`; HTTP routes use a per-request connection, `threading.local` only for long-lived threads.
- **Telemetry receiver:** bound once at service start on a loopback port (port 0, recorded in the settings table) and served by a **separate two-route app** (`/v1/metrics`, `/v1/logs`) on its own `uvicorn.Server` in the same event loop, so the main API is never reachable over TCP; `ecf claude` reads the port and asks the service for a per-session bearer token passed in `OTEL_EXPORTER_OTLP_HEADERS`; Content-Type checked (final Fable pass 2026-09-27).
- **Waiting and network:** while the secret store is locked, a desktop notification after 5 minutes, repeated hourly, and `status` shows the wait. Slack-health alerts use the same "network up" guard and 15-minute threshold as mail; posts are held, never dead-lettered, on network errors; `invalid_auth`/`account_inactive` alert at once.
- **Notifications:** `osascript` receives text only through `on run argv`, and notifications carry no email-derived text.
- **Backups and restore:** bundles are signed with a separate Ed25519 key whose signing seed is kept in the secret store (its seed is part of the backup key shown at `init`, below); `restore` and `import` verify it. Restoring a bundle signed by this install's own key resumes stages after `doctor` and shows the security-config and `SENDER#` differences; unsigned or foreign bundles follow the `import` rules (paused, capped at assist, announced diff). Import rejects `..`, absolute paths, symlinks and hardlinks, and caps decompression size. Restore requires confirming the old computer's service is stopped.
- **Rollback:** `ecf upgrade --to <previous>` keeps the sent, threads, senders and gate tables, rewinds the cursors so mail since the upgrade is re-fetched, and every address resumes paused and capped at assist.
- **Install method:** one supported method, `uv tool` (hatchling build, §14); the unit uses its absolute `ecf-server` path; `doctor` re-checks secret-store access after interpreter changes too, and `ecf upgrade` ends with that check and says what to click.
- **Unverified claims:** the `systemd-creds` TPM2/host-key and `LoadCredentialEncrypted=` behavior, Secret Service being unreadable before login, and "a live database copy isn't a consistent snapshot" for Time Machine. Export/import logging goes to local log files in v1 (`logs/_install/` is the M1 path).


**Final Fable pass (§10a) (final Fable pass 2026-09-27):**
- **Keychain:** the **service is the only writer** of secret-store items (the CLI sends an app password over the 0600 socket, as for PAM), so one binary owns the ACL. The V1.0 test covers service write, read after restart and read after `uv tool upgrade`, and whether other Python scripts can read the items silently. It is a gate: if they can, V1.0 adopts a private interpreter copy for ecf or items with `kSecAttrAccessControl` user presence.
- **Upgrade order:** stop the service → `uv tool upgrade` → `execv` the new `ecf-server migrate` (migrations belong to `ecf-server`) → start the service; nothing is imported from the old venv after the swap.
- **uvicorn:** pass `log_config=None` (so it doesn't add stderr handlers beside structlog) and set `uds=<path>` in `Config` for its log line, while `serve(sockets=[...])` does the binding. `init` and `doctor` check the socket path fits `sun_path` (104 bytes on macOS, 108 on Linux).
- **Backups:** changing the export keys or `export_dir` needs its own step-up whose prompt shows the new key fingerprint, and these are never accepted from `import`. `ecf init` shows one **backup key** string holding the age identity and the Ed25519 signing seed (keep it in your password manager); the running install also keeps the seed in its secret store to sign scheduled exports; `restore` on a new machine takes the backup key from you, stores the seed in the new secret store, and verifies bundles against the public key derived from it, never against a key inside the bundle. `ecf init --restore <bundle>` is the new-Mac path: install the package → `init --restore` → `slack set-tokens` → `address set --app-password` per address → `service install` → `doctor`.
- **Dead-man's switch (v1, no AWS):** every tick reschedules a Slack `chat.scheduleMessage` ("ecf hasn't checked in since <time>") a few intervals ahead and cancels it on a clean stop, so a stopped service, a tripped breaker or a dead laptop still reaches you in Slack.
- **PAM:** step-up attempts are rate-limited (`RATE#`) so a same-user process can't lock the OS account through `pam_faillock` (unverified).
- **After a reboot** the LaunchAgent runs only once you log in (README).

## 11. Security [v1 + M1-M3 as applicable]

- **Threat model** (SPEC owns; SECURITY.md summarizes): external sender (injection, BEC/invoice fraud, header forgery, MIME tricks, padding, reused Message-IDs, forged `SENT#` replies); a **lying or compromised watcher laptop**; a stolen laptop ([M1] or refresh token); a compromised Slack account; [M3] a compromised Claude account holding a connector token; **attacker text reaching a chat model that holds tools (confused deputy)**; [M1] the public endpoints ([M3] incl. `/mcp` called from Anthropic's servers) and flooding; malicious import bundles; the supply chain; insiders. **Stated limits:** in v1, anyone who controls your OS account controls ecf (secrets, state and service share one machine); from M1, anyone with admin AWS credentials bypasses every two-person rule and can delete logs.

  - **Mailbox:** credentials only in the broker (the local service's secret store in v1; `ecf-broker` in M1); all mailbox reads and mutations by the service, never by a model or client.

  - **[M1] `ecf-api` hardening:** fail-closed caller mapping; route scopes and per-client audiences (tokens from the remote-MCP or step-up client are rejected); body nonce plus timestamp; rate limits; audit of every call including denials; accepts client versions N and N-1.
  - **Step-up:** v1 OS authentication (Touch ID; PAM/polkit) bound to a single-use nonce; [M1] dedicated SRP-only Cognito client, nonce-bound, token in body, refresh revoked after use (§7).

### Group 1 results (docs research, 2026-09-26)

**Claude Code** (code.claude.com docs)
- Local plugin for testing: `claude --plugin-dir <path>` (documented).
- Hooks off: `disableAllHooks: true` (documented), but it also disables any custom status line (verified 2026-09-27, code.claude.com settings reference), so `ecf claude` uses a hook-free dedicated config instead.
- Transcripts: `cleanupPeriodDays`, default 30, minimum 1; stored at `~/.claude/projects/<project>/<session>.jsonl` (documented). `ecf claude` sets 1.
- claude.ai connectors excluded by `--strict-mcp-config`; also `disableClaudeAiConnectors: true` or `ENABLE_CLAUDEAI_MCP_SERVERS=false` (documented).
- Plugin subagents honor `model`, `tools`, `description`, `name`; ignore `hooks`, `mcpServers`, `permissionMode` (documented).
- `model` accepts aliases (`haiku`, `sonnet`, `opus`), full model IDs, or `inherit`; an alias resolves to the conversation's model when that is the same family (documented).
- **Resolved subagent model is not observable** (not documented; superseded 2026-09-27: observable via `/tasks` v2.1.242+ and telemetry, §5) → decided: full IDs pinned per release (decision 2 below).
- `claude "/loop …"` as the first prompt: docs say such sessions are grouped with non-interactive sessions and excluded from the session picker; how that interacts with Consumer Terms §3 is unclear. Moot: `/loop` was removed from v1 (decision 4).
- `/loop` jitter: up to half the interval for intervals under 1 hour; expiry 7 days (documented). Moot for v1 (`/loop` removed).

**Cognito and IAM** (docs.aws.amazon.com)
- Pre-token-generation V2 (Essentials) can **suppress `aws.cognito.signin.user.admin`** via `scopesToSuppress` and add claims; it runs after SRP + TOTP sign-in (`TokenGeneration_Authentication`) (documented). This fixes the Review 5 step-up token finding (the self-service scope); `ClientMetadata` from `InitiateAuth` is not passed to the trigger.
- App-client write permissions can be none only if the pool has **no required attributes** (documented). The pool defines none.
- Refresh token minimum 60 minutes; an app client may omit `ALLOW_REFRESH_TOKEN_AUTH`, but whether a refresh token is still issued is not documented (group 2).
- TOTP: ±30 s window documented; rejection of a reused code **not documented** (group 2). The server nonce remains the replay protection.
- Lambda execution-role trust: `aws:SourceArn`/`aws:SourceAccount` **not documented** for execution roles; Lambda offers `lambda:SourceFunctionArn` for identity policies. **Plan change:** no trust conditions on Lambda execution roles; rely on the permissions boundary (superseded 2026-09-27: the control is scoped `PassRole`, §10).
- Scheduler role trust: `aws:SourceAccount` + `aws:SourceArn` (schedule group ARN, not a schedule) documented, with example.
- Secrets write-only flow: `CreateSecret` + `PutSecretValue` (+ `TagResource` when tagging at create), no `GetSecretValue` needed; default key `aws/secretsmanager` needs no KMS grant (documented).
- CI policy checks: `cfn-policy-validator validate` on the synthesized template, free (`ValidatePolicy` no charge); custom checks $0.002 each, optional (documented).
- Lambda concurrency: new accounts get reduced quotas raised automatically with usage (no number documented); increases via Service Quotas; reserved concurrency must leave **100 unreserved** (documented). **Plan change:** reserve concurrency for broker and Slack only once the account quota leaves ≥ 100 unreserved; `init` requests the increase and skips reservation until then.
- PITR: **$0.20 per GB-month** us-east-1 (documented); pennies here.
- Cognito custom-domain CloudFront distribution is AWS-managed; `UpdateDistribution` scoping untested (group 2).

**Slack** (docs.slack.dev)
- `chat:write.customize` requires `chat:write`; sets `username`/`icon_url`/`icon_emoji` (documented). **Catch:** with customization, posting to a user ID lands in the Slackbot DM; DMs must use the `D…` ID from `conversations.open` (scope `im:write`). ecf never customizes DMs.
- Bot DMs: `chat.postMessage` to a user ID works with `chat:write` alone (without customization) (documented). Manifest: `messages_tab_enabled: true`, `messages_tab_read_only_enabled: true` (whether DMs show with the tab off is not documented).
- Private channels: `groups:write` covers create (`is_private`), invite, archive for bot tokens; `not_in_channel` errors documented.
- OAuth redirect must be HTTPS. `http://localhost` is treated as a PKCE desktop redirect, and **desktop redirects cannot request bot scopes** (documented), so PKCE-localhost is ruled out. Whether `https://localhost` works for a non-PKCE server flow is not documented: real-service test (a) stays gating.
- Configuration token expires after 12 h; `apps.manifest.create` needs `app_configurations:write` (documented).
- Free plan: 90 days visible, data older than 1 year deleted (documented; replaces rv).

**MCP** (modelcontextprotocol.io, python-sdk)
- Spec 2026-07-28 exists: stateless (no `initialize`, no sessions), `server/discover` required, `subscriptions/listen` replaces the GET stream, DCR deprecated in favor of CIMD (documented).
- Python SDK v2.0.0 released 2026-07-28 (latest v2.2.0, 2026-09-07); `FastMCP` → `MCPServer`; transport options move to `run()`/`streamable_http_app()`; bodies > 4 MiB → 413; serves 2025-era clients too (documented).
- Lambda: no official guide. Mangum pattern per SDK issue #3121: keep `MCPServer` at module scope, build `streamable_http_app()` inside the handler; `json_response=True`; set `transport_security` to the hostname (else 421). HTTP APIs buffer (streaming is REST-only), so JSON mode is required.
- **Open SDK issue #3357:** `MCPServer` always serves `subscriptions/listen`, which holds requests open until the Lambda timeout (one report: 99% of billed time). **Plan change:** remove that handler (private attribute today; revisit on SDK fix) and set the `ecf-mcp-remote` Lambda timeout to 29 s (the HTTP API maximum is 30 s).
- Tool annotations exist since 2025-03-26; claude.ai uses `readOnlyHint`/`destructiveHint` for auto-permissions in directory connectors (documented); behavior for unlisted custom connectors not documented. Users can set Always allow / Needs approval / Blocked per tool.

**Email providers** (sources: each provider's own help or documentation site, read 2026-09-26; see the IMAP provider compatibility table in SPEC, deliverable 1)
- **No hosted provider documents stripping forged Authentication-Results** (Purelymail, Gmail, Microsoft, Fastmail, iCloud, Yahoo/AOL, Zoho, Migadu, Proton). Microsoft's header carries no authserv-id; Yahoo (and reportedly Fastmail) use per-host IDs. Only self-hosted OpenDKIM (`RemoveARFrom`/`RemoveARAll`) or Postfix `header_checks` can be configured and proven.

- Purelymail app passwords give "full access to your email" (documented).
- Proton Bridge: no custom keywords (`\*` absent); labels appear as folders (evidence).

Commands: `ecf eval new-case --template <bec|injection|header|control>` (skeleton), `ecf eval build` (cards → `.eml` + `labels.jsonl`, validation, hygiene scan), `ecf eval show <id>` (renders the result as a mail client would).
7. **Verification:** the operator reviews each document when it is written (per the order of work above), including `LICENSE` (already committed) and `CLAUDE.md`; commit only on explicit confirmation.
