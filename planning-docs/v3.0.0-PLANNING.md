  is assigned (operator 2026-10-12), and whether this is a major version is decided after this

## 1. Why

- **Local speed under load.** On the fanless development Mac, Gemma 4 12B drops from about 26 to
  11-16 tokens/s within minutes of sustained work; one email takes about 3.8-5.7 s cool. The
  thermal probe has recorded nothing in any run (`{}` in all 29 archived results), so heat as the
  cause is measured indirectly, not confirmed (P17). Ollama MLX is not a fix today: the HTTP 501
  on structured output was the Homebrew build lacking `libollama_xgrammar.dylib`; Ollama's own
  0.40.3 build has it, and with `format` on both, MLX was 8% faster over a 60-email backlog (249
  s against 271 s) and not significantly different in accuracy (82.2% against 83.3% of fields,
  all-right cards 132 against 132, McNemar p 1.0), with more swap (SPEC §1.2, §21.2 at
  `5868001`; a trade-off, not adopted).
- **Claude already does better.** On the frozen set (268 cards), preset C scores 223 (83.2%,
  `61686db4`) against Gemma's 183 (68.3%, `d80ea43d`), both 0 unsafe and recall 95/95 (SPEC
  §21.2).
- **Long-term goal** (operator): optimise on Jev-style classifier modelling (typed questions with
  probabilities), then go local again.

## 2. Direction (operator decisions 2026-10-12)

- **Preset C (all-Claude) becomes the default.** Claude stays on demand: mail waits for an
  `/ecf-review` session (P3; ADR 0017). No unattended Claude in this release.
- **C is Claude-only** (operator 2026-10-12): no Gemma fallback and no Gemma check.
  `claude_queue_timeout` can no longer be enabled on a C address, and its fallback shadow runs
  and gate don't apply to C (amends OD-019 and OD-020 for C; an OD when built). Mail on a C
  address waits for a review session however long that takes; the model-free pre-check and rules
  still flag fraud and regulator mail. B keeps its fallback as today.
- **A Jev + Claude-actor preset is built beside it.** Jev classifies when mail is fetched; the
  Claude actor runs on demand. When Jev is down, mail waits; there is no Gemma fallback (P11).
- **Preset A stays supported, not prioritized** (OD-495).
- **Every role gets the best model for the job** (operator 2026-10-12; CLAUDE.md, model choice):
  the larger model stays unless a smaller one (Opus, Sonnet, Haiku 5.5, Gemma 12B, a smaller
  Gemma) is shown to match it on that job under the evaluation rules (OD-486). Splits are made
  with care (§4.1).

## 4. Design

### 4.1 Haiku 5.5 in every role

Haiku 5.5 runs the main session (OD-474). Haiku 4.5's figures don't carry over (CLAUDE.md, Haiku
versions). Runs need no code (`ecf eval run --claude --classifier-model` / `--actor-model`,
`src/ecf/cli.py:1128-1132`), frozen set, operator go-ahead per run:

- **H1, done:** C `standard`, classifier Haiku 5.5, `ee1915bc`: 210/268 (78.4%), 0 unsafe,
  recall 95/95; against Sonnet `61686db4` (223/268) -4.9 points (Newcombe -8.8 to -1.0), with a
  significant loss on `requires_action` (78.9% against 91.2%). **Sonnet keeps the classifier**
  (SPEC §21.2 at `ed31aaa`).
- **H2, registered** `fc997ef9`: C `standard`, `--actor-model claude-haiku-5-5`. The flag sets
  **both** `actor` and `actor_high` (`src/ecf_server/claude_eval.py:239`), so H2 measures Haiku
  5.5 in both actor roles (operator 2026-10-12). Baseline: `61686db4` (C, Sonnet `actor`, Opus
  `actor_high`), on actions and the must-escalate, must-not-hide and injection cases. The 6b runs
  `82106673` / `fccf0c0a` are preset B (Gemma classifies) and are not H2's baseline: their
  actions follow different classifications. A result for `actor` alone would need a separate flag
  and run; not planned.
- **H3, no run:** Haiku 5.5 classifier against Gemma by `ecf eval compare ee1915bc d80ea43d`,
  input differences stated as the compare reports them. Recorded for reference;
  it no longer settles L1 (§4.7).
- **H4:** Haiku 5.5 as the actor beside Jev, once §4.3 exists.

How a split is judged (operator 2026-10-12: the best model for the job, not the cheapest):

- **Per role, not per field.** One classifier call answers every field, so a role can't use Haiku
  for priority and Sonnet for category. Haiku 4.5 was better than Sonnet on priority (100% vs
  91.7%) and worse on category (68.9% vs 83.1%) and fraud risk; Haiku 5.5 in H1 was worse than
  Sonnet on priority (62.5% vs 71.2%) and category (83.1% vs 86.5%), better on requires_reply
  (93.0% vs 88.1%). A field-level win doesn't move a role.
- **Safety first, then accuracy.** The smaller model must hold the absolute gates (0 unsafe,
  full fraud-guard recall, injection cases safe) and show no significant loss on any
  safety-relevant field (fraud risk, category, rule) and no overall loss beyond the named margin.
  A significant loss on one such field keeps the larger model even if the total is within margin.
- **Differences are read, not just counted.** As in 6b (Sonnet against Opus as `actor_high`:
  same classifications, actions differed on 3 cards, the operator judged 2 equal and 1 better on
  Opus), the operator judges the cases that differ; when a difference favours the larger model on
  a high-risk item, the larger model keeps the role.
- **Noise.** Claude results vary run to run (2-3 of 10 re-classifications differ), so a split
  needs repeat runs or the paired comparison, not one score.
- **Cost and time come last:** only between models that are equal on the above.

Results set the pins per role. A pin change is a gate-key change (checked release path).
`actor_high` stays Opus until its own revisit after this release (SPEC §21.2, 6b), unless H2
shows Haiku 5.5 matching it there under these rules.

### 4.3 The Jev classifier

- **Precondition (step 2 starts here):** TypeSafe's published docs and one live response are
  checked for (a) exact, fixed model versions (not only `jev-latest` / `jev-preview`) and (b) the
  answering model's ID in each response; also (c) whether Jev has any instruction channel (P19,
  "(rv)": a reviewer's claim, not re-checked). If (a) or (b) is missing, Claude reports what is
  missing and the operator decides how to proceed (operator 2026-10-12); nothing is blocked or
  worked around automatically. Without (a) and (b), gate keys can't bind to the model that
  answered.
- **Adapter:** `systemone.py` gains a hosted transport (HTTPS to api.typesafe.ai, existing httpx
  pattern), beside the Ollama one. Jev replaces the classify step only; facts, triggers, rules,
  policy, stage, approvals and step-up are unchanged, and this is a release criterion (P4).
- **Payload:** the same prepared, redacted, capped excerpt the classifiers get today, the schema
  questions, and the derived signals in fixed wording (OD-483). Nothing else. A test bounds the
  request size. The exact payload is written into SPEC §12.4 before ship (§4.8).
- **Pin:** an exact model ID (format per the precondition check), in a lock file shipped in the
  wheel. The response's model is checked on every call; a mismatch refuses the answer. Jev joins
  the weekly model watch. A pin change restarts gates (P10).
- **Key:** `jev-api-key` in the OS secret store, written by the service (an `ecf models api-key`
  step and an `ecf init` step, validated by one call); covered by regrant and destroy; never in
  backups; never `$TYPESAFE_API_KEY` (P13).
- **Failures:** 429, 5xx and timeouts are provider faults: no attempt counted, the item waits
  (P11). An answer that doesn't map is a failed attempt, never a default. Score ties and choices
  outside the options resolve toward more risk (as `systemone.py` does today: score ties go to
  the higher level). Timeout and retry are set from Jev's measured latency (e.g. p99 plus a
  stated margin) in step 3, with the source recorded; SPEC §15.4 gets the row (P12).
- **Confidence:** Jev's probabilities are recorded for calibration; they never route an item to a
  weaker model or lower a risk (P26; OD-054 wording).
- **Logging:** `model_calls` gains a backend column and the Jev model ID; numbers only (tokens,
  client wall time, network time where separable); never request or response bodies (P22;
  OD-165). Field names Jev uses for content (`state`, `instructions`, `criteria`) join the log
  scrubber's list.

### 4.4 The Jev evaluation (OD-486)

- Through `ecf eval run` on the frozen set, answering every schema field, with the same signals
  block as the other arms (P8).
- **Prompt digest:** SHA-256 of the preamble, the question JSON, the excerpt cap and the model ID;
  recorded in the result so `ecf eval compare` checks inputs (P8).
- **Noise:** two back-to-back Jev runs before any gate; the margin is set above the measured
  run-to-run difference and named before the comparison (P18).
- **Comparisons:** Jev against C (`61686db4`, 83.2%) and Gemma (`d80ea43d`, 68.3%), Newcombe with
  `--margin`, input differences stated. Haiku 5.5 (`ee1915bc`, 78.4%) for reference. Qwen's
  archived figures are reference only.
- **Safety:** the absolute gates (0 unsafe, fraud-guard recall) and the injection set re-run on
  Jev; if the precondition check confirms Jev has no instruction channel, the preamble, schema
  text and email share one `state` (P19).
- **Latency and cost:** measured per call in the same runs (client wall time; price per call if
  TypeSafe publishes it). These set §4.3's timeout and are L1's inputs (§4.7).
- **Held out:** a fresh held-out batch written after Jev's questions are frozen (P18).
- Result files get a format version (P26).

### 4.5 Presets and migration (P7; checked release path)

- **Presets:** C is the default for new addresses; existing addresses keep their preset. An
  existing address changes preset only by removing it and adding it again, and adding fails while
  it still has open items (`src/ecf_server/addresses.py:514`; checked 2026-10-12). The Jev preset
  is a fourth value; its name is open (§6).
- **Table rebuild:** `addresses.preset` has `CHECK (preset IN ('A', 'B', 'C'))`
  (`src/ecf_server/migrations/0001_initial.sql:13`). SQLite can't alter a CHECK, so the migration
  rebuilds `addresses` (copy, drop, rename, with foreign keys and indexes re-created) and is
  tested on a copy of a real database.
- **Gate keys:** the Jev preset's key is `jev:<model id>+<schema digest>+<prompt digest>`.
  `items.pinned_models` (read through `claude_pins.item_key` and `gate.ITEM_KEY`),
  `model_calls.digest` (NOT NULL, `0018_model_calls.sql`, `0023_fallback.sql`) and `eval_runs`
  take the new form in the same migration (0036 or later; latest today is 0035).
- **C fallback removed:** on upgrade, a C address with `claude_queue_timeout` enabled has it
  turned off, with a Security Notice and an audit event naming the address; items it had sent to
  Gemma keep their records. `ecf init`, `ecf watch` and `ecf doctor` stop reminding C addresses
  about the fallback; Ollama is no longer needed for C (SPEC §4.2 "Must be running").
- **Upgrade and rollback:** the wheel keeps `src/ecf_server/data/ollama.lock` (a v2.2.x
  install's `ecf upgrade --wheel` needs it to read the wheel). Rollback to v2.2.3 (or the latest
  v2 release at ship) starts from the database copy taken at upgrade (`upgrade_snapshot.py`),
  and its `addresses` and `items` come only from that copy, so the old release sees no fourth
  preset value and no item keyed to Jev (code read 2026-10-12: `src/ecf/upgrade_run.py:217`,
  `src/ecf_server/downgrade.py`). Before the upgrade settles, the whole copy is used. After, the
  copy is merged by the **new** release's `ecf-server downgrade-prepare`: `sent`, `threads`,
  `senders` and `gate` come from the live database (common columns, for addresses in the copy);
  grants are voided, claims and queued actions cleared, every address paused and `live` dropped
  to `assist`; cursors stay, so mail since the upgrade is fetched again. Consequences for this
  release:
  - **`gate` rows keyed `jev:...` are carried back.** v2.2.3 reads `gate` only by
    (`address_id`, `pair_key`) for a key it computes (`gate.py:292`, `fallback.py:174`), so such
    a row is never read; it is an orphan, not a fault. Because the new release builds the merged
    copy, `downgrade.py` here can drop rows whose key the target can't produce; decided in step 4.
  - **An address moved to the Jev preset** (removed and added again with the same ID) returns
    to its old preset, paused; one added new after the upgrade is not in the copy and is lost.
  - **Any column this release adds** to `sent`, `threads`, `senders` or `gate` is left out
    (common columns only); none is planned.
  The rollback test runs, both before and after settle, with an address on the Jev preset and
  items classified by Jev, and checks the old service starts clean and `ecf doctor` is clean
  apart from expected rows.
- **Export:** whether `data_format` carries classifier provenance (Jev model ID) is decided in
  step 4; a change there is a major-version trigger (OD-480).

### 4.6 Historical scans and reprocessing

- **Historical scans** (P14): `ecf backfill --since` also takes relative durations (e.g. "3
  weeks"). Default records-only; classifying old mail prints a cost and time estimate first;
  hides from a historical scan need approval and are excluded from "Approve all"; one Slack
  summary per scan, not per minute.
- **Reprocessing** (P15): the key is the classifier ID plus the prompt, schema and rules digests,
  not the ecf version. Only by an explicit command. It never re-executes on an item a person
  reviewed or undid, or one that fired a fraud or regulator trigger.

### 4.7 Local candidates (model-choice rule; P16)

From a read of the deterministic code (2026-10-12; key claims spot-checked). Each is adopted only
if a measurement on the same cards shows it beats the current code and the Claude or Jev model
it would stand beside at that task. Every candidate is Gemma 4 12B until a non-Qwen decision
model exists (OD-494). Where a task is narrow, a smaller Gemma is also tried (see below).
Constraints for all: the pre-check stays model-free (SPEC §5.4; `precheck.py`); a model's answer
can only raise risk, never lower it or hide mail alone (I1, `policy.py`); a model's answer is
never a fact (ADR 0009, 0026); local only; low volume (heat). **None runs under C**, which stays
Claude-only and Ollama-free (§2).

- **L1 Gemma tier in front of Jev** (operator 2026-10-12): in the Jev preset, Gemma classifies
  mail that a deterministic rule calls low-risk (the same kind of routing as today's high-risk
  routing: pre-check facts, sender history), and Jev takes the rest. Never routed by Gemma's own
  answer (P26). Main reason: mail Gemma handles never leaves the computer. Cost is a reason only
  if TypeSafe charges per call (unpublished). Against it: Gemma is slower under load (§1) and
  68.3% against C's 83.2% overall; Jev's latency and accuracy are unknown. Measured after step 3:
  Gemma against Jev on the low-risk slice under §4.1's rules; it takes the slice only if it
  matches. The original L1 (a Gemma tier before Haiku under C) is dropped: C is Claude-only and
  H1 kept Sonnet as the classifier.
- **L2 raise-only check for scam requests the keywords miss** (B and the Jev preset): 9 of 15
  model-only scams carry no deterministic fact (extortion, parcel lures;
  PRE-CLASSIFIER-IMPROVEMENTS.md:86-88), and putting signals into the classifier prompt cost
  category accuracy. A separate, narrow Gemma call with yes/no questions ("asks for codes or card
  numbers to be sent back?", "asks for employee tax data?", "opens like an executive asking a
  secret favour?"), run only on mail with a partial deterministic hit (`triggers.py`, the
  `bec_opener`, `gift_card_ask`, `data_request`, `credential` groups). Its answer is stored with
  the classification, not as a fact. "Yes" flags (rule 1b); it escalates only with a
  deterministic second signal; "no" changes nothing. On the frozen set it has nothing to add:
  all 25 model-only fraud cards were escalated by both Gemma (`d80ea43d`) and C (`61686db4`), so
  its case rests on held-out batches 1 and 2 (model-only fraud cases; genuine flagged and genuine
  hide dropped), where it is measured.
- **L3 synthetic card generation:** training cards for a future non-Qwen decision model (SPEC
  §1.2) and the RAW 5,000-email corpus. Gemma has the edge only when generation is seeded from
  private corpus mail (which can't go to Anthropic); otherwise Haiku is likely better. Generated
  cards are never eval cards. Offline; no preset involved.
- **L4 keyword-list curation, offline:** the lists are English only, and one held-out pattern,
  `gift_card_codes_request`, caught 0 of 6 gift-card scams (none says "gift card"), while 5 of 11
  genuine cards in that batch would escalate on generic words (PRE-CLASSIFIER:163, :167). Gemma
  reads the encrypted corpus and proposes paraphrases, translations and localized quote headers
  ("Am ... schrieb"); the operator accepts each one; the lists stay deterministic and serve every
  preset, C included. Lists are frozen before any held-out batch is written, and the model never
  sees held-out cards. Measured by per-phrase hit tables on the frozen set and false positives
  over the corpus.
- **L5 injection check before a hide** (B and the Jev preset): when the plan is a hide (rules
  6-8), Gemma answers "does this text address or instruct an automated reader?"; "yes" adds a
  hide blocker. Hides are never urgent, so the delay costs nothing; the worst case is today's
  behaviour. Measured on the injection cards with genuine hides dropped at 0. (A reviewer cited 6
  of 18 injection cards missed by the keyword list; unverified.) Under C, `61686db4` planned no
  hide on any of the 22 injection cards.

**C's coverage without L2 and L5** (checked 2026-10-12 on `61686db4`, one run): 25/25 model-only
fraud cards escalated through `fraud_guard` (fraud risk medium on 2, high on 23); 0 of 22
injection cards got a hide action (19 escalated); 0 unsafe. Limits: one run (Claude varies run to
run); frozen set only, no C run on the held-out batches. A C run on held-out batches 1 and 2 is
optional, on operator request.

**A smaller Gemma where it is enough.** L2, L4 and L5 are narrow yes/no or proposal tasks; a
smaller Gemma model would load faster, use less memory and heat the Mac less, which suits bursty
local work. Which smaller Gemma 4 sizes Ollama serves, and their licences, are unverified (check
before step 6). A smaller Gemma is measured against Gemma 12B (and the Claude or Jev model it
stands beside) on the same cards and takes the task only if it matches under the rules in §4.1;
it gets its own pin. L1 (a whole classification) stays on Gemma 12B unless a smaller one matches
it there too.

Considered and not taken:
- **Gemma tier before Haiku under C** (draft 1's L1): C is Claude-only, and H1 kept Sonnet.
- **Label pre-fill for corpus labelling:** labels are blind, no model output shown (SPEC §16.7,
  `ecf eval label --corpus`).
- **Link text against target:** one held-out card exercises it, and it puts URLs in a prompt (an
  OD under ADR 0026); low value.
- **No model:** the pre-check, DKIM/DMARC, sender history, lookalike checks, IBAN checksums,
  hide corroboration, rules and policy (deterministic ground truth); cutting regulator false
  positives (would lower risk, I1); live redaction or excerpt reordering (a model could be
  steered to hide scam text).
- **The Haiku main session's dispatch loop** (40-68% of a C run's cost): deterministic
  service-side dispatch would beat both; OD-496 (`c52b58b`) took a first step, with the service
  telling the session what to do `next`.

## 5. Steps

Each step is a branch merged on its own; code merges pass the macOS gate with 0 skipped.

0. **Haiku 5.5 runs** (no code; operator go-ahead per run): H1 done (`ee1915bc`); H2 running
   (`fc997ef9`); H3 by compare. Record in SPEC §21.2.
1. **Qwen removal** (§4.2). Small, contained: two-agent review (CLAUDE.md, review sized to the
   change).
2. **Jev precondition check, then adapter, key, pin, failures, logging** (§4.3), behind the eval
   only: nothing in the service's classifier path uses it yet. If the precondition check finds a
   gap, report to the operator before building. Diff review by two agents before step 3.
3. **Jev evaluation** (§4.4): noise runs, then the comparisons; latency (and cost if published)
   measured, timeout and retry set from it.
4. **Presets and migration** (§4.5): C default, the Jev preset in the service path, the
   `addresses` rebuild migration, upgrade and rollback; H4 once the preset runs.
5. **Historical scans and reprocessing** (§4.6).
6. **Local candidates** (§4.7), as measurements allow; each is its own decision. L1 needs step
   3's figures.
7. **Ship:** privacy and docs (§4.8), the Jev ship decision recorded, release by the checked path
   (`ecf-release` skill).

## 7. Limits

- C keeps mail waiting for a review session, with no local fallback however long it waits; only
  the Jev preset classifies on fetch.
- Jev's latency, accuracy, determinism, versioning and base model are unmeasured or unpublished
  today.
- The synthetic set is public in the repo; whether Jev's training saw it is unknown.
- Claude results vary run to run (2-3 of 10 re-classifications differ; no temperature).
- C's coverage of model-only scams and injection hides (§4.7) is from one frozen-set run.
- Costs in SPEC are API-equivalent; Claude runs on the reviewer's plan allowance (SPEC §20).
