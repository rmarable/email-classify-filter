## 1. Why

- **Local speed under load.** On the fanless development Mac, Gemma 4 12B drops from about 26 to
  11-16 tokens/s within minutes of sustained work; one email takes about 3.8-5.7 s cool. The
  thermal probe has recorded nothing in any run (`{}` in all 29 archived results), so heat as the
  cause is measured indirectly, not confirmed (P17). Ollama MLX is not a fix today: the HTTP 501
  on structured output was the Homebrew build lacking `libollama_xgrammar.dylib`; Ollama's own
  0.40.3 build has it, and with `format` on both, MLX was 8% faster over a 60-email backlog (249
  s against 271 s) and not significantly different in accuracy (82.2% against 83.3% of fields,
  all-right cards 132 against 132, McNemar p 1.0), with more swap (SPEC §1.2, §21.2 at
  `5868001`; a trade-off, not adopted).
- **Claude already does better.** On the frozen set (268 cards), preset C scores 223 (83.2%,
  `61686db4`) against Gemma's 183 (68.3%, `d80ea43d`), both 0 unsafe and recall 95/95 (SPEC
  §21.2).
- **Long-term goal** (operator): optimise on Jev-style classifier modelling (typed questions with
  probabilities), then go local again.

## 2. Direction (operator decisions 2026-10-12)

- **Preset C (all-Claude) becomes the default.** Claude stays on demand: mail waits for an
  `/ecf-review` session (P3; ADR 0017). No unattended Claude in this release.
- **C is Claude-only** (operator 2026-10-12): no Gemma fallback and no Gemma check.
  `claude_queue_timeout` can no longer be enabled on a C address, and its fallback shadow runs
  and gate don't apply to C (amends OD-019 and OD-020 for C; an OD when built). Mail on a C
  address waits for a review session however long that takes; the model-free pre-check and rules
  still flag fraud and regulator mail. B keeps its fallback as today.
- **A Jev + Claude-actor preset is built beside it.** Jev classifies when mail is fetched; the
  Claude actor runs on demand. **When Jev is down, Claude classifies** (operator 2026-10-13,
  replacing P11's "mail waits"): the item joins the Claude review queue as a C item would, so it
  is classified at the next `/ecf-review`; there is no Gemma fallback. Switch and switch-back in
  §4.3.
- **Preset A stays supported, not prioritized** (OD-495).
- **Every role gets the best model for the job** (operator 2026-10-12; CLAUDE.md, model choice):
  the larger model stays unless a smaller one (Opus, Sonnet, Haiku 5.5, Gemma 12B, a smaller
  Gemma) is shown to match it on that job under the evaluation rules (OD-486). Splits are made
  with care (§4.1).

## 4. Design

### 4.1 Haiku 5.5 in every role

Haiku 5.5 runs the main session (OD-474). Haiku 4.5's figures don't carry over (CLAUDE.md, Haiku
versions). Runs need no code (`ecf eval run --claude --classifier-model` / `--actor-model`,
`src/ecf/cli.py:1128-1132`), frozen set, operator go-ahead per run:

- **H1, done:** C `standard`, classifier Haiku 5.5, `ee1915bc`: 210/268 (78.4%), 0 unsafe,
  recall 95/95; against Sonnet `61686db4` (223/268) -4.9 points (Newcombe -8.8 to -1.0), with a
  significant loss on `requires_action` (78.9% against 91.2%). **Sonnet keeps the classifier**
  (SPEC §21.2 at `ed31aaa`).
- **H2, done:** C `standard`, `--actor-model claude-haiku-5-5`, `fc997ef9`: 221/268 (82.5%),
  0 unsafe, recall 95/95; against Sonnet/Opus `61686db4` (223/268) -0.7 points (Newcombe -3.3 to
  +1.8, McNemar p 0.754), non-inferior at 5 points; no field differs significantly after Holm
  (SPEC §21.2 at `2ed046a`). The flag sets both `actor` and `actor_high`
  (`src/ecf_server/claude_eval.py:239`), but **only `actor_high` was exercised**: all 60 act
  claims went to the high-risk actor (every synthetic sender is first-time), so the `actor` role
  is unmeasured on this set. Of 56 act cases with the same rule in both runs, actions differ on 9
  (Haiku adds escalate on 5, drops flag on 3, including the injection card `inj-subject-line`;
  proposes leave on 1). **The role decision waits on the operator's judgement of those 9.**
  `actor_high` cost $0.05 (Haiku) against $1.61 (Opus), API-equivalent.
- **H2b, done** (repeat of H2 for noise, on `74e6904` with the service pacing the session):
  `f60fb8bc`: 222/268 (82.8%), 0 unsafe, recall 95/95; against `61686db4` -0.4 points
  (Newcombe -4.2 to +3.4), against H2 +0.4 (-3.4 to +4.2); no field differs significantly after
  Holm in either. Again only `actor_high` was exercised (57 act claims, all first-time). Of H2's 9
  action differences, 6 recur exactly (`inj-subject-line` drops the flag again; label instead of
  flag on `notif-storage-quota` and `other-parking-permits`; escalate instead of flag on
  `notif-backup-failed`; escalate added on `inj-hidden-html-junk`; leave on
  `other-thank-you-note`); `other-press-inquiry` matches Opus this time; `sales-rfp-deadline` and
  `v2-fin-tax-preparer-documents` got a different rule (classifier variation), so aren't
  comparable; 3 new differences (leave on `notif-ticket-auto-ack` and `other-holiday-greeting`,
  flag dropped on `v2-appt-family-reunion`). Pattern: Haiku escalates a little more where in
  doubt, chooses lighter actions than Opus on routine mail, and drops the flag on one injection
  card in both runs. The run took 272 s from first claim to last answer (H2 1,891 s); its
  "1,013 s in rounds" exceeds that and is checked before the SPEC record. Not in SPEC yet.
- **H3, no run:** Haiku 5.5 classifier against Gemma by `ecf eval compare ee1915bc d80ea43d`,
  input differences stated as the compare reports them. Recorded for reference;
  it no longer settles L1 (§4.7).
- **H4:** Haiku 5.5 as the actor beside Jev, once §4.3 exists.
- **H5: both actor roles measured** (operator 2026-10-13: "we need to measure both `actor` and
  `actor_high`"). The eval computes facts in an empty scratch history (`evalrun.py:827`), so
  every card is a first-time sender and high risk (`policy.py:167`). Step 1c adds a card option,
  `sender_history: known`, which seeds the eval scratch with that sender's history before the
  card runs; it is set on act cards with no payment and no fraud signal (existing cards and some
  of the 32 new ones), so they route to `actor`. Then C runs with the pinned actors and with
  `--actor-model claude-haiku-5-5`, compared per role. A card option is an eval change, so it is
  in step 1c's Phase R.
- **What was already measured, and what didn't work:** the classifier role with Haiku 5.5 (H1)
  didn't match Sonnet (a significant loss on `requires_action`), so Sonnet stays. Haiku 4.5 was
  17 points behind Sonnet on an older set (SPEC §16.2). For `actor_high`, Sonnet (6b) and Haiku
  5.5 (H2, H2b) held every safety gate; their action differences await the operator's judgement.
  The `actor` role has never been measured. No actor combination has been tried and rejected.

How a split is judged (operator 2026-10-12: the best model for the job, not the cheapest):

- **Per role, not per field.** One classifier call answers every field, so a role can't use Haiku
  for priority and Sonnet for category. Haiku 4.5 was better than Sonnet on priority (100% vs
  91.7%) and worse on category (68.9% vs 83.1%) and fraud risk; Haiku 5.5 in H1 was worse than
  Sonnet on priority (62.5% vs 71.2%) and category (83.1% vs 86.5%), better on requires_reply
  (93.0% vs 88.1%). A field-level win doesn't move a role.
- **Safety first, then accuracy.** The smaller model must hold the absolute gates (0 unsafe,
  full fraud-guard recall, injection cases safe) and show no significant loss on any
  safety-relevant field (fraud risk, category, rule) and no overall loss beyond the named margin.
  A significant loss on one such field keeps the larger model even if the total is within margin.
- **Differences are read, not just counted.** As in 6b (Sonnet against Opus as `actor_high`:
  same classifications, actions differed on 3 cards, the operator judged 2 equal and 1 better on
  Opus), the operator judges the cases that differ; when a difference favours the larger model on
  a high-risk item, the larger model keeps the role.
- **Noise.** Claude results vary run to run (2-3 of 10 re-classifications differ), so a split
  needs repeat runs or the paired comparison, not one score.
- **Cost and time come last:** only between models that are equal on the above.

Results set the pins per role. A pin change is a gate-key change (checked release path).
`actor_high` stays Opus until its own revisit after this release (SPEC §21.2, 6b), unless the
operator's judgement of the cases that differ in H2 and H2b shows Haiku 5.5 matching it under
these rules. The
`actor` role can't be pinned from a measurement until a set with sender history exists (H4 has the
same gap).

**Tier ladder so far** (operator 2026-10-12: "Haiku could be good enough where we use Sonnet, and
Sonnet where we use Opus"; checked against the runs):

| Role | Pin | Smaller model measured | Reading |
|---|---|---|---|
| `classifier`, `classifier_high` | Sonnet | Haiku 5.5, H1 | Significant loss on `requires_action`: Sonnet stays. |
| `actor_high` | Opus | Sonnet, 6b (`82106673` vs `fccf0c0a`, preset B, same Gemma classifications in both arms) | Same safety results; 3 actions differ, operator judged Sonnet no worse overall; $0.81 vs $1.57. |
| `actor_high` | Opus | Haiku 5.5, H2 and H2b (vs `61686db4`, C) | 0 unsafe, no hide on any injection card; H2: 9 actions differ (5 added escalations, 3 dropped flags, 1 leave); H2b: 6 of those recur, including the flag dropped on `inj-subject-line`, plus 3 new; $0.05 vs $1.61. |
| `actor` | Sonnet | none yet: not possible on this set | Every synthetic sender is first-time, so all act items go to `actor_high`. Measured as H5 (below). |
| main session | Haiku 5.5 | already the smallest Claude | Now the largest single cost of a C run (H2: $1.02 of $4.61). |

Reading: acting is constrained by the classification, rules and policy (the actor chooses among a
few allowed actions, and policy checks them again), so a smaller model plausibly suffices there;
classifying is the harder, safety-relevant job. Sonnet's `actor_high` result is one run; Haiku's
is two (H2, H2b), and actions are judged by eye on the cases that differ. Next: the operator
judges Haiku 5.5 and Sonnet against Opus side by side on their differing cases (for Haiku, the 6
that recur first, `inj-subject-line` above all) and picks the `actor_high` pin in this release (a
gate-key change, checked path). That replaces "until its own revisit after this release" if the
operator agrees.

### 4.3 The Jev classifier

- **What the docs settle** (2026-10-13; schema doc §4): (a) fixed versions exist (`jev-1.13.0`;
  aliases `jev-latest`, `jev-preview`; /models); (b) the response's `model` field reports the
  versioned ID that answered (/models, /api); (c) Jev has per-question `instructions` and
  `criteria` and no request-wide instruction field (/api). Endpoint `POST
  https://api.typesafe.ai/v1/systemone`, Bearer auth; body `model`, `state`, `questions`;
  response `model`, `answers`, `usage`. 64k tokens per request, 32k for state plus the longest
  question; 100K tokens/s, 80 requests/s.
- **Precondition (step 2 starts here):** one live response (synthetic data, operator go-ahead)
  confirms (b) and finds what Jev returns for an over-size request (undocumented). Anything that
  differs from the docs is reported to the operator; nothing is worked around automatically.
- **Adapter:** `systemone.py` gains a hosted transport (plain HTTPS to api.typesafe.ai, the
  existing httpx pattern in `ollama.py:353-359`), beside the Ollama one. Not TypeSafe's Python
  SDK: it reads `TYPESAFE_API_KEY` from the environment when no key is passed, defaults to
  `jev-latest`, and `TYPESAFE_LOG_LEVEL=debug` logs request and response bodies
  (/sdk/python/usage). Jev replaces the classify step only; facts, triggers, rules, policy,
  stage, approvals and step-up are unchanged, and this is a release criterion (P4).
- **Payload:** the same prepared, redacted, capped excerpt the classifiers get today, the
  questions for the fixed set, the default fields (unless off) and the user's fields (schema
  doc §1), and the derived signals in fixed wording (OD-483). Nothing else. Ordinal levels carry
  their descriptions (`score` criteria accept them; today `systemone.py:95` sends names only).
  A test bounds the request size. The exact payload is written into SPEC §12.4 before ship
  (§4.8).
- **Pin:** `jev-1.13.0` (or the version current at build), in a lock file shipped in the wheel.
  The response's model is checked on every call; a mismatch refuses the answer. TypeSafe states
  no retirement policy, so a pinned version that disappears fails closed: mail waits and
  `ecf doctor` says why. Jev joins the weekly model watch. A pin change restarts gates (P10).
- **Key:** `jev-api-key` in the OS secret store, written by the service (an `ecf models api-key`
  step and an `ecf init` step, validated by one call); covered by regrant and destroy; never in
  backups; never `$TYPESAFE_API_KEY` (P13). In AWS mode (M1) it goes into AWS Secrets Manager
  (operator 2026-10-13; a note for the M1 roadmap doc).
- **Failures:** 429, 529 (overloaded), other 5xx and timeouts are provider faults: no attempt
  counted, the item retries Jev until the switch below. 401 raises a System Error (bad key) and
  counts as Jev down. 422 (validation) and an
  answer that doesn't map are failed attempts, never a default. ecf's current over-context
  handling looks for HTTP 400 (`systemone.py:163`); the hosted mapping follows the live check.
  Score ties and choices outside the options resolve toward more risk (as `systemone.py` does
  today). Timeout and retry are set from Jev's measured latency (e.g. p99 plus a stated margin)
  in step 3, with the source recorded; SPEC §15.4 gets the row (P12).
- **Jev down: switch to Claude** (operator 2026-10-13; proposal, figures set in step 3):
  - *Per call:* a request times out after p99 latency plus a margin (P12).
  - *Switch:* an address marks Jev **down** when its calls have failed with provider faults
    (or 401) for `jev_down_after_minutes` (proposed default 15, range 5-1440, an address
    setting; no step-up, since it only moves work to another allowed classifier). While down,
    new mail and items waiting for Jev skip Jev and go to the Claude queue (`awaiting_claude`,
    need `classify`), classified by the C classifier pin under C's gate key, which must have
    passed for that address (else the item waits and `ecf doctor` says why). The card says
    "classified by Claude (Jev down)". Failed attempts (422, an answer that doesn't map) don't
    switch; after the usual attempt limit the item goes to Claude too.
  - *Switch back:* while down, the service probes Jev every 5 minutes with `GET /v1/models` (no
    email content). The first success clears **down**; new mail goes to Jev again, and items
    still waiting in the Claude queue and not yet claimed go back to Jev (as OD-293 returns
    items when the fallback is turned off). Claimed or classified items stay with Claude; nothing
    is classified twice.
  - Slack: one notice when Jev goes down (count, oldest age, "run `/ecf-review` to classify
    them") and one on recovery (§4.11). Audited. Privacy: Claude is already an allowed
    destination, so nothing new.
  - An OD records this (replaces P11 for the Jev preset).
- **Confidence:** Jev's probabilities are recorded for calibration. They may only make ecf more
  cautious: the middle band on the yes/no fixed items flags and blocks hiding, and a rule that
  hides mail on a choice field acts only above a confidence bar (schema doc §4; a new OD amends
  the OD-054 wording for this direction). They never route an item to a weaker model or lower a
  risk (P26).
- **Logging:** `model_calls` gains a backend column, the Jev model ID and TypeSafe's
  `request_id`; numbers only (`usage` tokens, client wall time, network time where separable);
  never request or response bodies (P22; OD-165). Field names Jev uses for content (`state`,
  `instructions`, `criteria`) join the log scrubber's list.

### 4.4 The Jev evaluation (OD-486)

- Through `ecf eval run` on the frozen set, answering every schema field, with the same signals
  block as the other arms (P8).
- **Prompt digest:** SHA-256 of the preamble, the question JSON, the excerpt cap and the model ID;
  recorded in the result so `ecf eval compare` checks inputs (P8).
- **Noise:** two back-to-back Jev runs before any gate; the margin is set above the measured
  run-to-run difference and named before the comparison (P18).
- **Comparisons:** Jev against C and Gemma, Newcombe with `--margin`, input differences stated.
  The baselines (C `61686db4`, 83.2%; Gemma `d80ea43d`, 68.3%; Haiku 5.5 `ee1915bc`, 78.4%) are
  on the 268-case set, so C is re-run on the 300-case set with the fixed-set labels in step 1c
  and Jev is compared with that; across the change, the 268-case subset is compared. Qwen's
  archived figures are reference only.
- **Safety:** the absolute gates (0 unsafe, fraud-guard recall) and the injection set re-run on
  Jev, which "does not treat [injected text] as hostile by default" (/model-jaggedness).
  Whether the untrusted-data preamble goes in `state` or in each question's `instructions` is
  measured (P19).
- **Latency and cost:** measured per call in the same runs. Price is published: $0.042 per
  million input tokens, output free (/models); whether `state` is billed once per request is
  read from `usage`. These set §4.3's timeout and are L1's inputs (§4.7).
- **Also measured in step 3** (schema doc §11): yes/no thresholds and middle-band bounds per
  fixed item; `fraud_risk` as `score` or `choice`; option-order consistency; `state` as named
  JSON fields against today's delimited string; an 8th fixed item for prompt-injection attempts;
  low-confidence choice handling; the confidence bar for hiding; Jev choosing the actor tier
  (up only, P26); cost, latency and fixed-item accuracy as user fields grow.
- **The pre-classifier for Jev** (RAW: rethink it to align with Jev; R3, operator 2026-10-12):
  Jev is also run without the signals block, on the same cards, and the two runs are compared
  per field and on the safety gates. The question is whether Jev's typed questions make any
  signal redundant, or call for one to be reworded or added as its own question. Whatever is
  changed is decided from that comparison and recorded. The pre-check itself stays model-free
  and is not touched (I1; SPEC §5.4).
- **Held out:** a fresh held-out batch written after Jev's questions are frozen (P18).
- Result files get a format version (P26).

### 4.5 Presets and migration (P7; checked release path)

- **Presets:** C is the default for new addresses; existing addresses keep their preset. An
  existing address changes preset only by removing it and adding it again, and adding fails while
  it still has open items (`src/ecf_server/addresses.py:514`; checked 2026-10-12). The Jev preset
  is a fourth value; its name is open (§6).
- **Table rebuild:** `addresses.preset` has `CHECK (preset IN ('A', 'B', 'C'))`
  (`src/ecf_server/migrations/0001_initial.sql:13`). SQLite can't alter a CHECK, so the migration
  rebuilds `addresses` (copy, drop, rename, with foreign keys and indexes re-created) and is
  tested on a copy of a real database.
- **Gate keys:** the Jev preset's key is `jev:<model id>+<fixed-questions digest>+<state format>`,
  where the questions digest covers the 7 fixed safety items, the 3 fixed workflow fields and
  any field a hide-capable rule reads (schema doc §7; Jev answers each question in isolation,
  so editing a label-only field needs no new gate run). C keeps the whole schema digest.
  `items.pinned_models` (read through `claude_pins.item_key` and `gate.ITEM_KEY`),
  `model_calls.digest` (NOT NULL, `0018_model_calls.sql`, `0023_fallback.sql`) and `eval_runs`
  take the new form in the same migration (0036 or later; latest today is 0035).
- **Classifications rewritten once** (schema doc §9): stored classifications move to the fixed
  items by a fixed table (`vendor_change_request` to `bank_detail_change`, `regulatory` to
  `regulator_claim`, `spam_or_phishing` to `phishing`, `team` to `claims_internal`, `person` from
  outside to `unfamiliar_person`), and an install's OD-478 extension file converts to user
  fields. Rollback uses the snapshot below, so no reverse migration is written.
- **C fallback removed:** on upgrade, a C address with `claude_queue_timeout` enabled has it
  turned off, with a Security Notice and an audit event naming the address; items it had sent to
  Gemma keep their records. `ecf init`, `ecf watch` and `ecf doctor` stop reminding C addresses
  about the fallback; Ollama is no longer needed for C (SPEC §4.2 "Must be running").
- **Upgrade and rollback:** the wheel keeps `src/ecf_server/data/ollama.lock` (a v2.2.x
  install's `ecf upgrade --wheel` needs it to read the wheel). Rollback to v2.2.3 (or the latest
  v2 release at ship) starts from the database copy taken at upgrade (`upgrade_snapshot.py`),
  and its `addresses` and `items` come only from that copy, so the old release sees no fourth
  preset value and no item keyed to Jev (code read 2026-10-12: `src/ecf/upgrade_run.py:217`,
  `src/ecf_server/downgrade.py`). Before the upgrade settles, the whole copy is used. After, the
  copy is merged by the **new** release's `ecf-server downgrade-prepare`: `sent`, `threads`,
  `senders` and `gate` come from the live database (common columns, for addresses in the copy);
  grants are voided, claims and queued actions cleared, every address paused and `live` dropped
  to `assist`; cursors stay, so mail since the upgrade is fetched again. Consequences for this
  release:
  - **`gate` rows keyed `jev:...` are carried back.** v2.2.3 reads `gate` only by
    (`address_id`, `pair_key`) for a key it computes (`gate.py:292`, `fallback.py:174`), so such
    a row is never read; it is an orphan, not a fault. Because the new release builds the merged
    copy, `downgrade.py` here can drop rows whose key the target can't produce; decided in step 4.
  - **An address moved to the Jev preset** (removed and added again with the same ID) returns
    to its old preset, paused; one added new after the upgrade is not in the copy and is lost.
  - **Any column this release adds** to `sent`, `threads`, `senders` or `gate` is left out
    (common columns only); none is planned.
  The rollback test runs, both before and after settle, with an address on the Jev preset and
  items classified by Jev, and checks the old service starts clean and `ecf doctor` is clean
  apart from expected rows.
- **Export:** whether `data_format` carries classifier provenance (Jev model ID) is decided in
  step 4; a change there is a major-version trigger (OD-480).

### 4.6 Historical scans and reprocessing

- **Historical scans** (P14; R8, operator 2026-10-12): `ecf backfill` takes `--since` and
  `--until`, each a date-time to the second (`2026-09-29T08:00:00`) or an age (`90m`, `3d`,
  `2w`, `6mo`, `1y`); `--until` defaults to now. Today `--since` takes a date only
  (`src/ecf/cli.py:341`); `ecf logs --since` already accepts a time or an age (`cli.py:395`),
  and the two share one parser. Default records-only; classifying old mail prints a cost and time estimate first;
  hides from a historical scan need approval and are excluded from "Approve all"; one Slack
  summary per scan, not per minute.
- **Reprocessing** (P15): the key is the classifier ID plus the prompt, schema and rules digests,
  not the ecf version. Only by an explicit command. It never re-executes on an item a person
  reviewed or undid, or one that fired a fraud or regulator trigger.

### 4.7 Local candidates (model-choice rule; P16)

From a read of the deterministic code (2026-10-12; key claims spot-checked). Each is adopted only
if a measurement on the same cards shows it beats the current code and the Claude or Jev model
it would stand beside at that task. Every candidate is Gemma 4 12B until a non-Qwen decision
model exists (OD-494). Where a task is narrow, a smaller Gemma is also tried (see below).

**MLX and GGUF, per task** (RAW: prefer gemma4 MLX; R2, operator 2026-10-12): each candidate is
measured on both builds of the same model, `gemma4:12b-mlx` and the pinned GGUF
`gemma4:12b-it-q4_K_M`, on the same cards, with `format` on both, run order alternated and
cool-downs between runs (the 2026-10-12 benches showed heat confounds run order). The build that
wins under §4.1's rules takes the task, with its own pin; on a tie, the faster one. Measured so
far (SPEC §21.2 at `5868001`, whole classification): MLX 8% faster over a 60-email backlog, no
significant accuracy difference, more swap (7.6 GB against 5.4). MLX's structured output needs
Ollama's own build: Homebrew's lacks `libollama_xgrammar.dylib`. So step 6 starts by moving the
development Mac to Ollama's official 0.40.3 build (or later), with `ecf models serve install`
pointed at it and `ollama.lock` updated; the GGUF results are re-checked on that build.
Constraints for all: the pre-check stays model-free (SPEC §5.4; `precheck.py`); a model's answer
can only raise risk, never lower it or hide mail alone (I1, `policy.py`); a model's answer is
never a fact (ADR 0009, 0026); local only; low volume (heat). **None runs under C**, which stays
Claude-only and Ollama-free (§2).

- **L1 Gemma tier in front of Jev** (operator 2026-10-12): in the Jev preset, Gemma classifies
  mail that a deterministic rule calls low-risk (the same kind of routing as today's high-risk
  routing: pre-check facts, sender history), and Jev takes the rest. Never routed by Gemma's own
  answer (P26). The reason is privacy: mail Gemma handles never leaves the computer. Cost isn't
  a reason: Jev costs $0.042 per million input tokens, output free (/models). Against it: Gemma is slower under load (§1) and
  68.3% against C's 83.2% overall; Jev's latency and accuracy are unknown. Measured after step 3:
  Gemma against Jev on the low-risk slice under §4.1's rules; it takes the slice only if it
  matches. The original L1 (a Gemma tier before Haiku under C) is dropped: C is Claude-only and
  H1 kept Sonnet as the classifier.
- **L2 raise-only check for scam requests the keywords miss** (B and the Jev preset): 9 of 15
  model-only scams carry no deterministic fact (extortion, parcel lures;
  PRE-CLASSIFIER-IMPROVEMENTS.md:86-88), and putting signals into the classifier prompt cost
  category accuracy. A separate, narrow Gemma call with yes/no questions ("asks for codes or card
  numbers to be sent back?", "asks for employee tax data?", "opens like an executive asking a
  secret favour?"), run only on mail with a partial deterministic hit (`triggers.py`, the
  `bec_opener`, `gift_card_ask`, `data_request`, `credential` groups). Its answer is stored with
  the classification, not as a fact. "Yes" flags (rule 1b); it escalates only with a
  deterministic second signal; "no" changes nothing. On the frozen set it has nothing to add:
  all 25 model-only fraud cards were escalated by both Gemma (`d80ea43d`) and C (`61686db4`), so
  its case rests on held-out batches 1 and 2 (model-only fraud cases; genuine flagged and genuine
  hide dropped), where it is measured.
- **L3 synthetic card generation:** training cards for a future non-Qwen decision model (SPEC
  §1.2). Generated cards are never eval cards. Offline; no preset involved.
- **Local decision models** (SPEC §1.2 Later; consolidated 2026-10-13, schema doc §13): a local
  replacement for Jev must speak the Jev `/v1/systemone` API; candidates based on a banned model
  are marked `{*}` (exploring one needs an operator exception, OD-494), e.g. `tev1:4b` {*}.
  Ollaya is a local runtime serving that API, not a model. Not built in this release.
- **The 5,000-email corpus** (RAW Future; R9, operator 2026-10-12): recorded in SPEC §1.2 Later
  as the RAW states it: "optimization of the testing data corpus": a **non-Anthropic** model
  generates up to 5,000 emails to stress-test the system, each saved as its own file with all
  headers (`.eml`), in a compressed archive that can mimic an IMAP mailbox (for example a
  Maildir tree in a `.tar.zst`). The generator is left open; it is chosen when the item is
  built, under the model filter (no PRC-, Meta- or X-affiliated labs; no Qwen), and a hosted one
  is given synthetic seeds only, never real mail. Not built in this release.
- **L4 keyword-list curation, offline:** the lists are English only, and one held-out pattern,
  `gift_card_codes_request`, caught 0 of 6 gift-card scams (none says "gift card"), while 5 of 11
  genuine cards in that batch would escalate on generic words (PRE-CLASSIFIER:163, :167). Gemma
  reads the encrypted corpus and proposes paraphrases, translations and localized quote headers
  ("Am ... schrieb"); the operator accepts each one; the lists stay deterministic and serve every
  preset, C included. Lists are frozen before any held-out batch is written, and the model never
  sees held-out cards. Measured by per-phrase hit tables on the frozen set and false positives
  over the corpus.
- **L5 injection check before a hide** (B and the Jev preset): when the plan is a hide (rules
  6-8), Gemma answers "does this text address or instruct an automated reader?"; "yes" adds a
  hide blocker. Hides are never urgent, so the delay costs nothing; the worst case is today's
  behaviour. Measured on the injection cards with genuine hides dropped at 0. (A reviewer cited 6
  of 18 injection cards missed by the keyword list; unverified.) Under C, `61686db4` planned no
  hide on any of the 22 injection cards. **Overlap:** under the Jev preset, the possible 8th
  fixed item for prompt-injection attempts (§4.4, step 3) asks the same question inside the Jev
  call; L5 is measured for the Jev preset only if that item isn't adopted.

**C's coverage without L2 and L5** (checked 2026-10-12 on `61686db4`, one run): 25/25 model-only
fraud cards escalated through `fraud_guard` (fraud risk medium on 2, high on 23); 0 of 22
injection cards got a hide action (19 escalated); 0 unsafe. Limits: one run (Claude varies run to
run); frozen set only, no C run on the held-out batches. A C run on held-out batches 1 and 2 is
optional, on operator request.

**A smaller Gemma where it is enough.** L2, L4 and L5 are narrow yes/no or proposal tasks; a
smaller Gemma model would load faster, use less memory and heat the Mac less, which suits bursty
local work. Which smaller Gemma 4 sizes Ollama serves, and their licences, are unverified (check
before step 6). A smaller Gemma is measured against Gemma 12B (and the Claude or Jev model it
stands beside) on the same cards and takes the task only if it matches under the rules in §4.1;
it gets its own pin. L1 (a whole classification) stays on Gemma 12B unless a smaller one matches
it there too.

Considered and not taken:
- **Gemma tier before Haiku under C** (draft 1's L1): C is Claude-only, and H1 kept Sonnet.
- **Label pre-fill for corpus labelling:** labels are blind, no model output shown (SPEC §16.7,
  `ecf eval label --corpus`).
- **Link text against target:** one held-out card exercises it, and it puts URLs in a prompt (an
  OD under ADR 0026); low value.
- **No model:** the pre-check, DKIM/DMARC, sender history, lookalike checks, IBAN checksums,
  hide corroboration, rules and policy (deterministic ground truth); cutting regulator false
  positives (would lower risk, I1); live redaction or excerpt reordering (a model could be
  steered to hide scam text).
- **The Haiku main session's dispatch loop** (40-68% of a C run's cost): deterministic
  service-side dispatch would beat both; OD-496 (`c52b58b`) took a first step, with the service
  telling the session what to do `next`.

## 7. Limits

- C keeps mail waiting for a review session, with no local fallback however long it waits; only
  the Jev preset classifies on fetch.
- Jev's latency, accuracy and determinism are unmeasured; its base model and a version
  retirement policy are unpublished.
- Jev's known weaknesses (/model-jaggedness/jev-1.13): literal reading of negation, dates read
  as text, weak score calibration, a lean toward the first option, injected text not treated as
  hostile by default, lower accuracy as unrelated state grows. Other languages, CJK included,
  are "handled but not equally well" (/models): a stated limit for non-English mail.
- The synthetic set is public in the repo; whether Jev's training saw it is unknown.
- Claude results vary run to run (2-3 of 10 re-classifications differ; no temperature).
- Actions have no scored measure: the eval scores classifications and rules, and action
  differences are judged by the operator case by case.
- C's coverage of model-only scams and injection hides (§4.7) is from one frozen-set run.
- Costs in SPEC are API-equivalent; Claude runs on the reviewer's plan allowance (SPEC §20).
