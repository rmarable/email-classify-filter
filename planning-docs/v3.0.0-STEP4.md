## 1. What step 4 is
A preset D address's new mail is classified by TypeSafe Jev shortly after its pre-check; the
actor stays Claude at `/ecf-review`. While Jev is down, D mail waits. Facts, triggers, rules,
policy, stages, approvals and step-up are unchanged (release criterion P4, PLANNING §4.3), apart
from the "unsure" caution of §4. Plus the six step-5 hand-offs (STEP5 §8) and JEV-STEP2's
step-4 items.

**Not step 4:** the figures (step 3: timeouts, retries, breaker, `jev_down_after_minutes`,
attempt limit, band lower bounds, confidence bars, cost per email); H4 (Haiku 5.5 as D's actor;
later, `eval-` keyed, same source run); user fields on D (refused, S4-D6); the Claude fallback
(v3.0.1 candidate); the final privacy statement (step 7), though §12.4's payload line must be
true for D at merge.

## 2. The service path

### 2.1 Where D items wait (S4-D1, P13)
- D items wait at `awaiting_claude` with no classification, like C's, so no new status and no
  `items` rebuild. `route_new` and `_SWEEP` route D as C (every `preset = 'C'` literal is
  enumerated and widened where D belongs: claude_queue.py:43, :88-96, :112-118, claude_review
  `_WAITING`, config.py:1116, about 8 in all, P13).
- `/ecf-review` never offers a D item for **classification**; it offers D items for the
  **actor** as for C.
- D items waiting for Jev are excluded from C's `backlog`, `waiting`, `overdue` and the
  reminder and escalation; the daily summary and `ecf status` gain a "waiting for Jev" count.

### 2.2 The worker (S4-D3, P4, P6, P12)
- **Module:** `jev_dispatch.py`, imported only by `service.py` and `api.py`, enforced by a new
  import-linter contract (beside the existing "classifier never imports jev"). It computes D's
  gate key and prompt digest from `jev.py` and writes them where readers need them (pin and
  gate rows, `pinned_models`); modules in `classifier`'s import closure (108 of ~120: cards,
  backfill, health, alerts, gate, claude_pins, settings, importer, evalrun, stages, ...) read the
  stored values, or `jev.lock`/`jev_mapping.json` through a tiny loader with no `jev` import
  (P6). `jev.py` is not split; a test pins `gate_key` and `prompt_digest` byte for byte.
- **Thread:** the 60 s tick starts a one-shot drain thread when D items wait and Jev isn't down
  and no drain is running (the pattern of `_model_watch` and `_export`); `route_new` also sets
  an event the tick reads, so new mail waits at most one tick. The drain classifies until the
  queue is empty, Jev goes down, or the service stops. Concurrency 1 (step 3 S3-D4).
- **Pick (P3, P9, P12):** in one write transaction: the oldest **unmarked** (new) D item, then
  marked (historical) ones, by `claude_since`, from addresses with `paused = 0 AND removed_at IS
  NULL` and a stored D consent marker (§3.1); no live or held claim, a claim counting as live
  until `expires_at + GRACE`; the drain inserts its own claim (session `jev`) so `/ecf-review`
  can't take the item meanwhile.
- **Request:** `jev.Email` built from the item exactly as `claude_review.get_message` builds
  Claude's (sender, subject, `internaldate`, attachments with the same inline/name filter,
  `excerpts.classifier_text`, OD-483 signals), redaction always on, default format and preamble.
- **Store (P3, S12):** `classifier.store(..., provider="jev", expected=AWAITING_CLAUDE)`, whose
  classify UPDATE gains `AND classification IS NULL`, checks the row count, and writes no audit
  row when it touched none; then the transition and `decide.apply` as for C.
- **Service-mode Jev client (P4):** no run budget, no run stop event, no in-call cool-down: a
  fault returns at once with its class; the drain records it and stops; the tick decides when
  to try again. Tested: `classify` in service mode never sleeps longer than one short
  `Retry-After`. The httpx client is recreated after a transport error following a wake.
- **Liveness (P4):** the drain publishes last-run and last-ok times in `ServiceState`; when D
  items wait and no drain has progressed for `jev_down_after_minutes`, the tick treats Jev as
  down (§2.3). `ecf status` and `ecf doctor` show the drain's state.

### 2.3 Failures and Jev down (S4-D2, OD-510, P2(a), P10, P11)
- **Per item (P11):** only item-specific failures, a request error after the first successful
  call or an unmapped answer, count toward the attempt limit (placeholder 3), stored as
  `facts.jev_attempts` (not the unused `model_attempts` column, P7). At the limit the item
  waits with a System Error naming it (no Claude fallback); `ecf doctor` lists it.
- **Down, per install (S4-D2):** one Jev state per install, stored in a service-written settings
  row (one writer: the tick). Down when provider faults have lasted `jev_down_after_minutes`
  (install setting, default 15, 5-1440, no step-up) of **awake, online** time: the timer resets
  on wake and doesn't run while `health.resolves(api.typesafe.ai)` fails (P4). Down **at once** on
  an auth failure (401, 403, the key gone), a retired or changed pin (a failing probe, or
  request errors on N consecutive distinct items, placeholder 3), or a `Retry-After` past the
  short tier (P10).
- **A locked Keychain** (the secret store unavailable) is a quiet pause: no attempt counted, no
  alert, no down timer, as the mail checks treat it (P4).
- **While down:** D mail waits; the drain isn't started. **Switch back:** the probe (the
  key-check call, no email content) at each cool-down end, 30 s doubling to 5 min, run by the
  tick in a one-shot thread; up after K consecutive successful probes (placeholder 2).
- **Notices (hand-off 1, P10):** `open_alert("jev_down", "install", detail)` once, with the
  count of D items waiting, the oldest age, and the reason (faults, the key, the pin: "upgrade
  ecf" for a retired pin, which never recovers by itself); detail updated while down;
  `resolve_alert` on recovery; both audited. Re-opens capped per day. New kind in
  `health.TITLES`, `NOT_CHECKS`, `alerts.CLASS_OF`.

### 2.4 The pin and the mapping in upgrades (S4-D12, P18)
- Every reply's `model` must equal `jev.lock`; a mismatch marks Jev down with the pin reason.
- `jev.lock` and step 3's `jev_mapping.json` are read by `ecf/upgrade_check.read_wheel` as wheel
  files (as `ollama.lock` is today), not as `release.json` fields; a change to either in an
  upgrade names the D addresses that drop to assist (their gate key moves).
- The model watch records the Jev aliases' `release_date` from `GET /v1/models` (hand-off 6).

## 3. Preset D on an address

### 3.1 Adding a D address (S4-D11, P9)
- `addresses.PRESETS = ("C", "D")`; `importer.validate` stops refusing D.
- `ecf address add --preset D` and the `ecf init` preset prompt: refused unless the TypeSafe key
  is stored (checked by secret name, no `jev` import); a step-up (D3); and a typed consent
  answer: "Has the account owner agreed to their mail going to TypeSafe (api.typesafe.ai, US),
  as well as to Anthropic? [y/N]". The service refuses without `owner_agreed` (a body flag on
  `addresses.add`, not the converted-address machinery, P22); an audit row with no content.
- **The consent marker travels with nothing (P9):** stored per address (e.g.
  `addresses.overrides.jev_consent_at`); `ecf resume` of a D address without it asks the same
  question; the drain checks it before every call (fails closed); import and restore clear it.
- `ecf init` gains the key step when D is chosen (`ecf models api-key set --provider
  typesafe` underneath; one validating call; Security Notice).
- A preset changes only by remove and re-add.

### 3.2 The gate for D (S4-D5, P5, P8, P2(a))
- **One gate row per D address**: D's own (no C row; P2(a)). `claude_pins.PAIR["D"] =
  "jev/claude"`, `GATE_ROLES["D"] = ("actor", "actor_high")`; D's key combines the stored Jev
  gate key (§2.2) with the actor pins.
- **Synthetic evidence (P8):** a complete, pinned `/ecf-eval --preset D` run whose Jev source run
  is: `redact` true, complete, `for_gate` not false, the current pin and `prompt_digest`, the
  current `jev_mapping.json` digest, every D case present; the D Check prints the source run id
  and pin. `GATE_BACKENDS` isn't the mechanism (P8: the sentence is dropped).
- **Scored with the band (P5):** one shared function derives the unsure set and below-bar fields
  from the probabilities, used by the service and by the D eval (`_jev_run` returns probabilities);
  `gate.synthetic` refuses a D run scored without it; gate cases include ones whose expected rule
  is reached only through a banded item.
- **The key moves with the mapping (P5):** `mapping_digest` = the canonical digest of
  `jev_mapping.json` (per-field lower bounds, bars, thresholds, tie rule); a change demotes a
  live D address (stages.tick); test. No D gate run counts before step 3's figures are in the
  mapping (P11 of measurement).
- **Determinism (P16):** the source run's determinism figures are shown in the D Check (field
  flips, faulted pairs); step 3 supplies the margin.
- Gate key shape: four parts, `jev:<pin>+<questions digest>+<state format id>+<mapping
  digest>` (S4-D10).

Refused in v3.0.0 (default schema only), decided with S4b. S4's `preset == "C"` checks are
widened only where they must refuse D too; the apply-time privacy line names TypeSafe for D.

## 4. Unsure and confidence (S4-D7, P1, P14, P15, P17, step 3 P10/P11, OD-511)
- **Rule (P1, agreed with step 3):** the stored yes/no stays `p >= 0.5`. `jev_mapping.json` holds,
  per banded field, a lower bound `lo < 0.5` (the loader refuses `lo >= 0.5`); a probability in
  `[lo, 0.5)` makes the field **unsure**. Above 0.5 it's a yes, as today.
- **Banded fields:** the five safety yes/no items (`bank_detail_change`, `regulator_claim`,
  `phishing`, `claims_internal`, `private_individual`), `payment_related`, and the hide-read
  `requires_action` (step 3 P11); `fraud_risk` gets a raise-only bar on `p(none)` (P17; step 3
  sets it); workflow fields otherwise get no band.
- **Effect:**
  - Rules read the stored field, so an unsure field fires no rule (as today).
  - `schema.fixed_item`, `policy.payment_or_fraud` (policy.py:167-171) and the other direct
    `payment_related is True` readers treat unsure as yes: step-up, Approve-all exclusion,
    batch risk, own review, alert items (P1 reader list).
  - Every hide on an unsure or below-bar case is **dropped** (leave and flag, the
    policy.py:212-217 path), junk included, never an approve-mode hide (step 3 P10); an unsure
    `phishing` blocks junk from any non-fixed rule.
  - `requires_action` unsure is treated as yes in `actor.allowed` (no hide actions).
  - The card names the unsure field ("unsure: phishing"); that is the "label" (no rule fires).
  - Property test: no case is less cautious than with no band (P26).
- **Confidence bar:** a rule that hides on `category` or `sender_type` acts only when that
  field's confidence (defined as the chosen option's probability) is at or above its bar; below
  it the hide is dropped and flagged. OD-511 amends OD-054.
- **Storage (P14, P15):** beside the classification, not inside it (validation is
  `extra="forbid"`): `facts.jev` holds `unsure` (names), `below_bar` (names) and the per-field
  probabilities and confidence (numbers only, I5/OD-165), kept as long as facts. A reader that
  misses `facts.jev` behaves as today, never below it.
- **Review accuracy (P14):** a Fix that sets an unsure field to yes counts as a correct
  "unsure", not a gated-field miss (defined in `review.py`); stated in SPEC §9.3.

## 5. Records, cards, estimates
- **`model_calls` (hand-off 5, P7):** migration 0040 adds nullable columns by `ALTER TABLE`:
  `backend`, `model`, `fault`, `ms`, `tries`. `prompt_tokens` holds input tokens; `role` is
  `classifier` or `probe` and `outcome` `ok`, `error` or `timeout` (0018's CHECKs already allow
  them). One row per Jev call. No rebuild, so older bundles import unchanged; `ecf stats` gains a
  Jev line. Migration number after step 5's 0039; `release.json` `schema_version` follows.
- **Cards (hand-off 2):** step 5's display-name map gains "TypeSafe Jev <version>" from
  `jev.lock`; the unsure line (§4).
- **D's estimate (hand-off 4, P20):** Jev cost from the latest Jev run's `input_tokens_billed /
  n` (else the live check's 2,374 tokens per item, labelled) at US$0.042 per million; the
  Claude actor's share labelled as an estimate (classifier and actor sessions aren't separable in
  `claude_calls`); time from Jev's measured latency. Docs say D's case is immediacy, not cost
  (C classification counts against the Claude plan; D adds a small TypeSafe bill).
- **Reprocess on D (S4-D16):** goes to the Jev drain, new mail first (P12).
- **Doctor (S4-D18):** the key, the pin, the mapping, the down state and reason, the drain's
  state, D addresses without consent, items at the attempt limit.

## 6. Upgrade, rollback, export (S4-D13, S4-D14, P19)
- Rollback restores the snapshot's addresses; a D address added after the upgrade is lost;
  `downgrade.py` drops `jev:` gate rows; mail Jev classified after the upgrade is re-fetched and
  its actions may run again under the older version's path (stated).
- The TypeSafe key stays in the Keychain after a rollback (v2.2.x doesn't know its name):
  `downgrade-prepare` deletes it, or the release notes say how.
- Export: `pinned_models` and `facts.jev` carry the provider, model and unsure data; no
  `data_format` change.
- The checked release path's `ecf1009` cycle includes a D address with Jev-classified items.
