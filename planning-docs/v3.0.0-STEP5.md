## 3. 5a. Time ranges and historical scans

### 3.1 One range parser (D3; P13)
`ecf/timerange.py` (client; `ecf_server` imports it to validate, as it imports `ecf.errors`).
Users: `ecf backfill`, `ecf reprocess`, `ecf logs` (gains `--until`), `ecf stats --since`.

| Form | Example | Meaning |
|---|---|---|
| date | `2026-09-01` | start of that day, local |
| date-time | `2026-09-29T08:00[:SS]`, `"2026-09-29 08:00"` | that moment |
| zone | `…Z`, `…-04:00` | as given; no zone = Mac local |
| bare time | `08:00`, `08:00:30` | today, local; refused if in the future (no roll-back) |
| age | `90s 30m 2h 3d 2w 6mo 1y`, compound `1h30m` | before now; `mo` = 30 d, `y` = 365 d |
| anything else | `3 days`, `3M`, `30min` | refused; the hint lists the short forms (RAW's `min/hr/day/week/month/year` map to `m h d w mo y`) |

- Lowercase, case-sensitive units. A local time in a DST gap is refused; in a fold, refused with
  both UTC readings shown (P13).
- Output always `%Y-%m-%dT%H:%M:%S.%fZ` (matches `ecf logs`' string compare, `audit.py:81-83`).
  The resolved range is echoed in UTC before anything runs; the typed string is kept in the
  `backfill.started` / `reprocess.started` audit row.
- **N-1 client (P13):** `POST /v1/backfill` still accepts a bare date (UTC midnight, as today,
  `fetch.py:323`) for the v2.2.x client; the new client never sends one. SPEC §15.1 lists both.
  `api_version` stays 1.

### 3.2 Backfill ranges (D5; P7)
- At `start`, once: `SEARCH SINCE (since − 1 day) [BEFORE (until + 2 days)]` (IMAP SINCE/BEFORE
  ignore time and zone, RFC 3501 §6.4.4), then `FETCH INTERNALDATE` of the two boundary days only
  to cut to the second. Store the first and last UID in `Backfill` (in `settings`; a row without
  them reads as today). Pages then walk that UID range; no SEARCH per page.
- Mail ecf holds is skipped (`known`) and counted; mail after time=0 that retention deleted is
  read again (records-only unless `--act`); a re-read fraud item is re-reported "found in old
  mail" (P28, stated).
- `fake.py` models server-zone INTERNALDATE dates.

### 3.3 `--act`: count, estimate, cap (D6; P1, P11)
- **Count (a job under the address lease, next check; the CLI polls; P11):** in range, minus held,
  = K to classify. "N in range, M already held, K to classify." May be stale by one check; said.
- **Estimate (P1):** K × API-equivalent per item, from this install's `claude_calls` /
  `claude_sessions` over the last 30 days (classifier, actor and main-session share per item,
  cache reads included); with fewer than 50 items there, SPEC §21.2's whole-run figures (US$0.024-
  0.038 per card on schema v2, `10.25/268` and `6.45/268`, +16-21% Sonnet input on v3), named as
  such. Time: "about T minutes of `/ecf-review` session time" from `claude_sessions`
  items/(ended − started) median, else "not measured yet". Plus: "while these wait, new mail is
  reviewed first; they don't count toward the reminders" (§2).
- **Cap, in the service (P11):** `backfill.start` refuses `act` with K > 500 unless given a
  step-up nonce bound to {address, since, until, act, K}. `--yes` skips the question, never the
  step-up. Splitting a range evades the cap (accepted for cost; stated).
- D's estimate: step 4 (P22 hand-off, §8).

### 3.4 Slack: one summary per run (D8; P10)
- **At run start:** the head post (address, range, mode) in the alerts channel.
- **As found:** fraud and regulator items as thread replies, one line each in the burst-card
  style (kind, sender, subject, id; `escalations.py:162-174`), up to 20 per reply; a fraud reply
  mentions the member (SPEC §5.4). Records-only finds are labelled "found in old mail, no action
  taken". Above 20 lines a new reply starts; no "by id only" overflow.
- **At the end and as items settle:** the head is edited in place (`slack_out` updates by key):
  fetched, recorded, classified, waiting for `/ecf-review`, approvals pending (`ecf approve --scan
  <id>`), fraud, regulator. It keeps updating until the last marked item leaves the C queue, so a
  `--stop` or reset summary isn't stale (P10).

### 3.5 Approving a run's hides (P9)
`ecf approve --scan <run id>`: lists every pending hide of the run (sender, subject, action),
then one step-up bound to that exact grant set (as `approve_batch`, `approvals.py:203-210`).
Single `ecf approve <id>` still works. Not part of "Approve all".

### 4.2 Command (D10 as amended by P5; P8)
`ecf reprocess <address> --since … --until … [--rules-only] [--force] [--dry-run]`:
- **Eligible:** items ecf holds in its database, status `observed` or `executed` (allow-list,
  P3), **and** not reviewed or corrected (`items.review`), **and** no fraud, fraud_weak or
  regulator trigger (`facts.triggers`) (D11); everything else is skipped and counted by reason.
  (Amended 2026-10-14: draft 3 as first committed lost D11's review and trigger skips.)
- **Per item, the minimum (P5):** reclassify when `classifier`, `prompt` or `schema` differ;
  re-plan only when just `rules` differs. `--rules-only` never calls a model. `--force`: all
  eligible items, default mode.
- **Guards:** `--dry-run` (and the default first screen) shows "N reclassify, M re-plan only, K
  would touch the mailbox; skipped: …". Confirmation always; step-up when reclassify > 500 or
  mailbox-touching > 500, bound like §3.3. Items with no classification (records-only, pre-check
  only) are skipped by `--rules-only` and counted (P5).
- **Runs as a service job (P8):** batches of ≤ 50 items per transaction, progress in `settings`
  (like `Backfill`), `ecf reprocess --status`, `--stop`; no IMAP or model call inside `write_tx`.
- `item.reprocessed` audit row per item (old and new key); marked `facts.reprocess` (§2); one
  summary per run (§3.4).

### 4.3 State and execution (D11; P3)
- New edges, guarded by `TransitionContext.reprocess`: `observed → awaiting_claude | classified`
  and `executed → awaiting_claude | classified` (reclassify), `observed → proposed`,
  `executed → proposed` (re-plan). SPEC §6.2 and the §22.1 diagram test updated.
- Reprocessing items are excluded from `close_gone` (`fetch.py:733-774`) while marked in flight.
- **Executed items whose `done` holds a move (archive, junk, move):** the new classification and
  plan are recorded, **no mailbox action runs**; the summary lists "plan now differs: N" with ids.
- Executed items still in INBOX: added labels applied; an added hide proposed for approval (§2);
  dropped labels left and counted.
- `_remember` appends to `done` (keeps the original move record), never replaces (P3).
- **`ecf item undo <id>` (new, P3):** the digest's Undo (`digests.py:208-235`) as a command, using
  `mailbox_actions.undoable`'s checks; the "now wouldn't hide" summary line points at it.

## 7. 5e. `spam_or_phishing` → `phishing`, rename only (D17; P21; PH1, PH2)

- **Rename:** fixed rule #5 id and label (`fixed_rules.yaml:73-76`); keyword
  `$ecf_<install>_phishing`. The old id refused in a user rules file **as a rule id only** (it stays
  allowed as a user label, `test_policy.py:82`), with a hint. `convert_v2` runs at every service start
  (`service.py:609`) and on import and restore (`importer.py:162`), and decides "fixed" by
  `fixed_ids()` (`rules.py:760-763`); the removal keeps it and `starter_rules_v2.yaml`. So
  `convert_v2` and `_v2_fixed` also treat the legacy id `spam_or_phishing` as fixed: an identical v2
  copy is stripped as before, a customised one stops the conversion as before (its System Error
  names the rename). Without this, every v2 install whose applied rules copy the starter file
  would keep the old rule as its own, the old-id check would refuse the file, and the starter
  rules would apply (P21, checked 2026-10-14). Test: a v2 applied file with the starter
  `spam_or_phishing` rule converts cleanly after the rename. Label vs field name `phishing`: checked against
  `_check_label_from` and the reserved-name builder (`config.py:683-713`).
- **Eval (P21):** no expected rule and no archived result uses rule 5 (0 of 42 results), so
  nothing to map in compare; set version unchanged; no gate-key effect. Unit tests updated:
  `test_fixed_rules.py:40, :75, :130-131`, `test_rules.py:147-150`, `test_policy.py:523`. No new
  synthetic card.
- **Why (S4 D6b; reason confirmed by the operator 2026-10-14):** rule 5 fires on schema v3's
  fixed item `phishing: true`, not on spam, so its id and label should name that item.
- **No relabel (PH1, operator 2026-10-14, OD-508).** Nothing in ecf reads a keyword's name: Undo
  removes the keyword the item's own `done` record names, skipping `NEVER_UNDONE`
  (`mailbox_actions.py:288-296`); restore and second-install detection read only the
  `$ecf_<install>_` prefix, case-insensitive (`keywords.py:33-42`); `facts.ecf_keywords` is read
  for presence only. Keywords don't show in Gmail's or Purelymail's interface, and the affected
  mail shrinks with retention (90 days) and provider Spam purging. A relabel would have needed
  folder-scoped IMAP operations, a crash-safe swap, rollback handling, an I2 exception and a
  two-provider live check (PH3-PH10). So: new mail gets `$ecf_<install>_phishing`; mail labelled
  before keeps `$ecf_<install>_spam_or_phishing` and still undoes. No I2 exception; SPEC §8.3's
  announcement of one (SPEC.md:964) is withdrawn.
- **Legacy ids (PH2):** one `LEGACY_FIXED_IDS = {"spam_or_phishing": "phishing"}` read wherever
  `fixed_ids()` is consulted: `_check_user_rule` (`rules.py:440-442`), `check_layers` /
  `default_rules_off`, `convert_v2` / `_v2_fixed`, `config._schema`'s reserved names.
- **A user rule already named `phishing` (PH2):** allowed today, refused after the rename, which
  would stop the whole applied file compiling at upgrade (the default rules would apply, with a
  System Error). The upgrade check reads the old service's applied rules and refuses the upgrade,
  naming each user rule id or `default_rules_off` entry that equals a new fixed id and the rename
  to make; the System Error names the rename too. Tests for both ids.
- `NEVER_UNDONE` unchanged (D17). No migration.
- **Release note:** "Mail ecf labelled as phishing before v3.0.0 keeps the keyword
  `$ecf_<install>_spam_or_phishing`; new mail gets `$ecf_<install>_phishing`. Undo works on both."
