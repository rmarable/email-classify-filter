# v3.0.0 - Remove Local Models & Implement Jev as Classifier

Save this document to planning-docs/VERSION-3.0.0-PLANNING.md when it is approved.

# Problem Statement
Very poor performance is observed from local models on MacBook Air; the most likely is heat buildup from heavy GPU usage as this machine has no fan.  Impossible to remediate - will only be worse with cheap corporate laptops.

# Updated Architecture
Before, we had local Gemma as classifier and as an option for the action model.

Now:
- TypeOne Jev as the classifier
  - https://docs.typesafe.ai/cookbooks
  - https://docs.typesafe.ai/introduction
  - https://docs.typesafe.ai/models
- Claude as the decider/action
  - optimize usage of Haiku, Sonnet, and Opus based on their strengths
  - ensure high performance and accurate, consistent, and verifiable decision-making
- Locally-hosted Ollama (gemma4-mlx:12b) for any pre-classifier or pre-decision activities where calling Haiku would be overkill
- Improve deterministic steps to make better use of Jev/Claude capabilities

# Updated Behavior
When ecf is installed, the installer provides:
- Email addresses to monitor (Gmail or IMAP mailboxes)
- Authorized operators
- TypeSafe Jev API key

- Operators can:
  - use the provided default schema, or provide their own customized YAML input file
  - use my minimal set of provided actions (which are very bare bones), and add their own to meet their business needs
      - Example: put a "Soccer" tag on any email in my Gmail Inbox that talks about World Cup, USMNT tickets, etc.)

Every N minutes, ecf will poll the mailbox for new messages, classify them with Jev against the current schema, then perform the defined action(s) based on the classification results.
- By default, ecf only starts monitoring from time=0.
- Offer the ability to perform historical classification/actions based on either absolute or relative time ranges (HH:MM:SS, N min/hr/day/week/month/year, something along those lines)
- Don’t reprocess mail again if the ecf version, schema, or actions have not changed since the previous scan (i.e. don’t repeat work that has already been done, but if want to revisit messages with updated software, I can)

Since we’re using frontier models now, we shouldn’t need to train anything locally so any existing pre-classifier logic should be rethought to align with Jev.  Optimize usage of Haiku, Sonnet, and Opus based on their strengths to ensure high performance and accurate classification/decision-making.  When performing pre-classification or pre-decision activities, it is appropriate to recommend the use of a local Ollama-hosted model in place of Haiku.
- Prefer Gemma4 MLX models on Ollama in your recommendations (gemma4:12b-mlx)

Since the Qwen and tev1 models failed to outperform Gemma, remove them completely and restore Qwen and Qwen-based models to the banned model list.
