## Context

Users supply their own classification fields on top of a small fixed set that ecf owns and
users can't remove. The classifier (Jev or Claude) answers the fixed set, a replaceable default
schema and the user's fields in one request. ecf's safety rules read only the fixed set and
computed facts. This builds on today's OD-478 extension (`ecf/schema.py:13-15`,
`extend_schema`) rather than replacing it, and replaces today's safety core inside `category`
and `sender_type` (`SAFETY_FIELDS` / `SAFETY_VALUES`, `ecf/schema.py:43-55`).

## 2. Format and validation

- YAML with `fields`; each field has a `type` (enum, ordinal or yes/no), a `description`, and
  values or levels each with a description. **No free-text type** (model-written text would
  reach storage and Slack; privacy).
- **Descriptions are required** on every field, value and ordinal level, in user and starter
  schemas; ecf refuses a schema missing any (decided 2026-10-13). Jev never sees field or
  value names, only descriptions (TypeSafe agent skill, `SKILL.md`, read 2026-10-13). The
  starter `priority` gains level descriptions (today it has names only).
- **Catch-all warning:** ecf warns when an enum has no catch-all value (`other`, `none` or
  `unknown`, S4 D15). Jev's `choice` always picks an option, and TypeSafe advises a no-match
  outcome. A user field may reuse `other`, `unknown` or `none` as its own value; a
  `{label: {field: x}}` rule is refused on a field whose values repeat another field's value
  or a label name (S4 P12, 2026-10-14).
- **Descriptions naming a fixed field are refused** (S4 P10, 2026-10-14): a user description
  that names one of the 11 fixed field names is refused at apply (descriptions reach the
  classifier as instructions); naming a default or user field warns (S4 D9b).
- **Reserved names:** user YAML can't use a fixed-safety or fixed-workflow name, nor today's
  reserved names (`RESERVED_FIELDS`, `ecf/schema.py:288`).
- **Size:** user fields are for preset C only (S4 D8, 2026-10-14; D's handling in step 4). The
  S4 refusals for A or B addresses and C's local fallback go with the removal (ADR 0031): no such
  address or setting is left. In v3.0.0 today's caps
  apply to C (8 fields, 16 values, 180-character descriptions, 4,000 characters;
  `ecf/schema.py:289-293`) (S4 D7). The 16 KB rendered budget for Jev and Claude and the
  schema sent once per agent (P11) move to step 3: Claude's agents get the schema in every
  item read today (`claude_review.py:512-514`), and a read result past ~40 KB spills to a
  file. Cost, latency and fixed-item accuracy as fields grow are measured in step 3. Jev's own
  limits apply (§4).
- **Where it lives** (P16): no separate file; the `schema` section of the `ecf config apply`
  document, stored in `settings` (`config.py:295-316`). `CURRENT_VERSION = 3`,
  `schema_v3.yaml`, `release.json` `classifier_schema: 3`.
- **One schema per install** for v3; per-mailbox schemas go to SPEC §1.2 Later.
- **Who may change it:** an admin CLI change with step-up (`config_apply`, `config.py:688`),
  never through MCP.
- **Where it is written** (operator decision 2026-10-14; settled in S4, OD-502): the `schema`
  section of an `ecf config apply` file with `version: 1`, like every other section; no separate
  schema file or version key. The examples below show the section's content (the `version: 3`
  line and the path were placeholders, kept as written in draft 3).

## 3. Examples

A user field (the `schema` section of an `ecf config apply` file; adds to the default):

```yaml
version: 1
schema:
  fields:
    department:
      type: enum
      description: Which of our groups this email is for.
      values:
        compchem:    Computational chemistry: molecular modelling, simulation, quantum chemistry, docking.
        compbio:     Computational biology: genomics, sequence analysis, protein structure, systems biology.
        informatics: Research informatics: data platforms, pipelines, LIMS, databases, IT for research data.
        other:       None of our groups.
    about_soccer:
      type: boolean
      description: The email is about soccer, e.g. the World Cup, USMNT matches or tickets.
```

Rules that use them (RAW's "Soccer" tag example is the second):

```yaml
rules:
  - id: route_compchem
    when: {field: department, eq: compchem}
    then: [{label: compchem}]
  - id: soccer
    when: {field: about_soccer, eq: true}
    then: [{label: soccer}]
```

The classifier is asked `department`, `about_soccer`, the default fields and the ten fixed
fields together. Fixed safety rules run first, so a fraud email is escalated whatever its
`department`.

## 4. Classifiers

Both classifiers get the fixed set, the default fields (unless off) and the user's fields.

### Claude (preset C)

Already classifies against the live schema: `config.current_schema` (`claude_review.py:432`),
sent as a JSON schema plus each field's description (`claude_review.py:489-491`), answers
checked against it.

### Jev (verified against docs.typesafe.ai, 2026-10-13)

- **What it is:** a hosted System One decision model: typed questions (`choice`, `score`,
  `noul`) about a `state`, a probability per option; it "does not generate text" (ADR 0028;
  /introduction/coding-agents).
- **Endpoint:** `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer <key>`;
  body `model`, `state`, `questions` (the fields ecf sent to Ollama's `/v1/systemone` before the
  removal, minus `keep_alive`); response `model` (the versioned ID that answered), `answers`, `usage`
  (/api).
- **Questions:** per-question `instructions` and `criteria`, no request-wide instruction field.
  `choice` criteria map option to description (at most 255 options); `score` criteria are an
  array of level descriptions (2-10 levels), so ordinal levels can carry their definitions
  (today `systemone.py:95` sends level names only); `noul` takes optional `true`/`false`
  criteria (/api, /primitives/noul).
- **Isolation:** "every question is evaluated in parallel and in isolation against the same
  state"; Jev "ingests the state once" (/introduction, /models). User fields shouldn't change
  the fixed items' answers.
- **Limits:** 64k tokens per request (state plus all questions), 32k for state plus the
  longest question; 100K tokens/s and 80 requests/s, "adjusting dynamically" (/models). No
  stated cap on question count or instruction length. No Gemma-style caps for Jev.
- **Errors:** 401, 422 (validation), 429, 529 (overloaded); no 400 listed, and over-limit
  behaviour isn't documented (/api). The adapter maps 422 to a failed attempt and 429/529 to
  a provider fault (item waits); ecf's current over-context handling looks for HTTP 400
  (`systemone.py:163`). Over-size behaviour is found by a live test.
- **Pin:** `jev-1.13.0`; aliases `jev-latest`, `jev-preview` (/models). No deprecation policy
  is stated: a pinned version disappearing fails closed (mail waits, `ecf doctor` row).
- **Price:** $0.042 per million input tokens; "Output tokens are free" (/models). Whether
  `state` is billed once per request is implied ("ingests the state once"), confirmed from
  `usage` in step 3.
- **Known weaknesses** (/model-jaggedness/jev-1.13): literal reading of negation; dates read
  as text; score calibration "weak"; "leans toward the option that comes first"; "does not
  treat [injected text] as hostile by default"; accuracy falls as state grows with unrelated
  content. Other languages, incl. CJK, are "handled but not equally well" (/models), a
  stated limit for SPEC.
- **Transport:** plain HTTPS (`ecf_server/jev.py`; `ollama.py` goes with the removal, ADR 0031), not
  TypeSafe's Python SDK: the SDK reads `TYPESAFE_API_KEY` from the environment when no key is
  passed (forbidden, ADR 0028), defaults to `jev-latest`, and `TYPESAFE_LOG_LEVEL=debug`
  logs request and response bodies (no payload logging) (/sdk/python/usage). Log
  `request_id` and `usage` only.
- **Not answered by the docs:** Jev's base model (OD-494 needs a written vendor answer before
  use); the SDK's question `weight` field.

### How Jev's answers are used

- **Middle band** (decided 2026-10-13): for the six yes/no fixed items, an answer inside a
  middle band is "unsure": the email is labelled and flagged for a person, never hidden, and
  an unsure item blocks hiding as a yes does (I1). Only a clear yes drives the item's rule
  (`phishing` junks only on a clear yes). Bounds are placeholders (e.g. 0.3-0.7), set per item
  in step 3. TypeSafe: "Lower it when missing a true yes is expensive, such as failing to
  flag a safety issue"; send middle values to a person (/primitives/noul). Jev only: Claude
  answers true/false.
- **Confidence-gated hiding** (decided 2026-10-13): a rule that hides mail on a choice field
  acts only above a confidence bar, else flags or leaves the mail. The bar is set in step 3. A
  new OD amends "confidence-based routing would be a separate decision" (SPEC §7.7, OD-054
  wording) for this cautious direction only. After /patterns/confidence-routing.
- Probabilities otherwise never route an item to a weaker model or lower a risk (P26).

## 5. Rules and actor

- **Order:** fixed safety rules first (fraud_guard, regulatory, fraud_weak,
  unverified_payment_sender, junk), then the user's rules, then the default rules. First
  match wins.
- **Ownership** (decided 2026-10-13): the 16 starter rules (`starter_rules.yaml`) split into
  5 fixed and 11 default:

  | # | Rule | Then | Hide | v3 |
  |---|---|---|---|---|
  | 1 | `fraud_guard` | label suspicious, flag, escalate | never | fixed |
  | 2 | `regulatory` | label regulatory, flag, escalate | never | fixed |
  | 3 | `fraud_weak` | label suspicious, flag | never | fixed |
  | 4 | `unverified_payment_sender` | label unverified_sender, flag | never | fixed |
  | 5 | `bug_report` | label; flag/escalate by priority | corroborated | default |
  | 6 | `invoice` | label; flag if deadline; leave | corroborated | default |
  | 7 | `payment_confirmation_remittance` | label | corroborated | default |
  | 8 | `account_security` | label, flag | corroborated | default |
  | 9 | `shipping` | label, leave | corroborated | default |
  | 10 | `appointment_school_family` | label; flag if deadline | corroborated | default |
  | 11 | `travel_finance` | label | corroborated | default |
  | 12 | `spam_or_phishing` | label, junk | corroborated | fixed (reads `phishing`) |
  | 13 | `marketing` | label, archive | corroborated | default |
  | 14 | `automated_notification` | label, mark_read, archive | corroborated | default |
  | 15 | `requires_reply` | label, flag; actor | corroborated | default |
  | 16 | `otherwise` | actor | corroborated | default |

  Users may add rules and edit or remove default rules; fixed rules can't be touched.
- **Fixed rules read only the fixed set and computed facts.**
- **Validation:** a user rule naming a missing field or an illegal value makes
  `ecf config apply` refuse the file, naming each bad reference and how to fix it (as today:
  `rules.py:400-425`). A **default** rule naming a value the user removed is disabled
  instead, and `ecf config apply` says clearly which rules were disabled, why, and how to fix
  each.
- **Policy applies to every rule:** I1 (no hide without corroboration, never on `high`, never
  with a fraud, regulator, unscanned or quarantine signal), I2 (nothing removes a label or
  flag). A user rule that tries to archive phishing mail is blocked.
- **Actor trigger:** the rule's `actor:` key (`none`, `continue`, `continue_if`), which
  already exists (`starter_rules.yaml:72,128`; `rules.py:163`).
- **Actor limits stay in code** (P4, 2026-10-13; reverses the 2026-10-12 decision):
  `actor.allowed` keeps reading `requires_reply`/`requires_action` (`actor.py:94-96`), which
  are fixed fields and always present. That is a floor: a rule could later only narrow it,
  never grant a hide the floor refuses (OD-250).
- **Actor tier:** Jev choosing the actor tier (Haiku/Sonnet/Opus) from an intent or
  complexity question is measured in step 3 (/patterns/intent-routing). P26 applies: no
  routing down to a weaker tier on a model answer unless a new OD says so. On the synthetic
  set every act claim goes to `actor_high` (first-time senders), so the `actor` tier needs
  cases that reach it.

## 6. User-defined actions (examples; illustrative, not designed)

The operator would like users to add new kinds of action. The shape below is invented.
Actions are declared once and used in rules like a built-in action; payloads are filled only
from a fixed variable list: `{sender}`, `{subject}`, `{date}`, `{address}`, `{labels}`, any
schema field's value (enum, ordinal or yes/no), `{item_link}`. Never the body, never
model-written text.

```yaml
actions:                       # invented shape
  notify_compchem:
    type: slack_post
    channel: "#compchem-mail"
    text: "{sender} - {subject} ({department})"
rules:
  - id: route_compchem
    when: {field: department, eq: compchem}
    then: [{label: compchem}, notify_compchem]
```

| Example | Where data goes | New destination? | Reversible | Proposed policy |
|---|---|---|---|---|
| `slack_post` to another channel | Slack, same workspace | No: Slack already receives subjects, senders, classifications (SPEC §12.4) | No | automatic; channel allow-listed |
| `webhook` (HTTPS POST of variables) | the URL's owner | **Yes**, per URL | No | URL allow-listed with step-up; secret in the OS store; `live` only; send limits |
| `calendar_event` in macOS Calendar, or an `.ics` file in a local folder | this computer | No | Yes | one-click approval; date from a deterministic parser, never a model guess (Jev reads dates as text) |
| `calendar_event` in Google Calendar | Google | **Yes**, plus OAuth (Gmail is IMAP only, OD-425) | Yes | as webhook, plus an OAuth design |
| `task` in macOS Reminders | this computer | No | Yes | automatic or approval, per action |
| `task` in Todoist, Asana, Jira or Linear | that service | **Yes**, per service | Mostly no | as webhook; API key in the OS store |
| `run_local` (a user script, variables as JSON on stdin) | wherever the script sends it | Unknown | No | step-up to register the script (path and hash); never body text; never on fraud or regulator items |

Proposed limits for every custom action: `live` only (local-only actions in assist is an
operator decision); fixed rules can't use them; the actor can't propose them; every run
audited; an unknown outcome is never retried (as sends, SPEC §8.4); a new destination needs
an operator decision and a SPEC §12.4 line before it is enabled. Not in v3 unless decided:
OAuth integrations; model-extracted dates or task text.

## 7. Gates

- **Eval gate** measures only the fixed safety set end to end (0 unsafe, fraud-guard recall).
- **Jev gate key** (decided 2026-10-13): the 7 safety items, the 3 fixed workflow fields, any
  field read by a rule that can hide mail (`HIDE_ACTIONS`, `rules.py:62`), the Jev pin and
  the state format. Editing a label-only or flag-only field needs no new gate run under Jev;
  when one is needed, it runs automatically (API calls on the frozen set).
- **Claude (C)** (P12): the same key as Jev's: the fixed fields plus any field a hide-capable
  rule reads (today the whole schema digest, `claude_pins.py:138-140`). An edit that changes
  the key applies, live addresses drop to assist with a warning first (`config.py:99,779`),
  and ecf tells the operator to run `/ecf-eval`. A label-only field edit needs no new run.
- **Live (go-live) gate** (decided 2026-10-13): today it needs category accuracy (100 reviewed
  at 85%, `high` 200 at 90%; SPEC §9.3). It becomes accuracy on the 7 fixed safety items and
  3 fixed workflow fields from reviewed mail, plus no fraud-guard misses; user fields are
  reported, not gated. Thresholds carried over unless measurement says otherwise.

## 10. Eval

- **Labels** (P8): fixed-item labels derived at load from today's labels by the §9 table, so
  card text and hashes don't change and nothing is re-confirmed; two-agent review of the

  report-only (no pin or gate decision).

## Verification (tests when built)

- A schema with no user fields yields the 7 + 3 fixed questions; YAML can't define a
  fixed-safety or fixed-workflow name, nor redefine one.
- A schema missing any description is refused; an enum with no catch-all value warns.
- Jev questions carry the `fraud_risk` level definitions.
- `ecf config apply`: a user rule with a missing field or illegal value refuses the file and
  names it; a default rule naming a removed value is disabled and listed with its fix.
- A user rule that tries to archive phishing mail is blocked by policy; a middle-band answer
  never hides mail and blocks hiding.
- Sender confirm works with no `category` field.
- `actor.allowed` refuses hides on actionable mail whatever rule continued the item (P4).
- A split answer can't happen: the starter `category` and `sender_type` lack the values the
  fixed items carry; `hide_blockers` blocks on each fixed item (P1).
- The Jev gate key changes for a hide-capable field and not for a label-only field.
- Migration: one-time rewrite and snapshot rollback on a copy of a real database.
- The frozen set on C, then on Jev: 0 unsafe and fraud-guard recall using only the fixed set.
  S4's user layer is measured by the S4 plan's M2 against the S3b pair (S4 P5, P6).
