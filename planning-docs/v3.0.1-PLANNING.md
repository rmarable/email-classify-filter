# v3.0.1: the `actor_high` pin (plan)

Draft 1, 2026-10-14. **Folded into v3.0.0 as PLANNING step 6** (operator decision 2026-10-15,
OD-517); was scheduled for immediately after `v3.0.0`. Not designed in detail yet; this records the
scope and the evidence so far, and step 6's plan starts from it.
SPEC §21.2 (H2, H2b, 6b) holds the runs.

**After the removal of Gemma and Ollama** (v3.0.0, ADR 0031, OD-506): preset B is gone. The 6b
evidence below used preset B source runs (Sonnet and Opus acting on the same Gemma
classifications); those runs stay as history and can't be repeated. Whether D's eval source query
may accept a C result as its source, which would give an actor-only comparison on frozen
classifications again, is decided in v3.0.1 (operator decision 2026-10-14; removal P19). Step 2d
builds D's source query for Jev runs only; adding a C source is a small addition to that query.

## Decision so far

- `actor_high` stays `claude-opus-5-5` through `v3.0.0`. The operator chooses its pin in v3.0.1
  after more data (operator decision 2026-10-14), leaning towards Haiku 5.5 or Sonnet 5.5 on
  price. This replaces "revisit after `v3.0.0`" (SPEC §21.2, 6b).
- A pin change is a gate-key change: checked release path (SPEC §1.4, OD-492); `live` addresses go
  back to `assist` until their gate passes again.

the 13 cards. Only `actor_high` was exercised (every synthetic sender is first-time).

**Cost** (API-equivalent, per act claim): Opus about US$0.027, Sonnet about US$0.013, Haiku about
US$0.001 (SPEC §21.2).
These are API-equivalent figures; on the operator's Claude plan the cost is usage limits. They
become real per-token costs once Claude runs through Bedrock (roadmap M4, SPEC §1.2) or the API, so
the operator weighs the choice with Bedrock in mind (operator 2026-10-14; Bedrock prices for these
models unverified).

## Open before the choice

- **The plan's rule** (v3.0.0 PLANNING §4.1): "when a difference favours the larger model on a
  high-risk item, the larger model keeps the role". Every act item here was high-risk, and Opus
  was preferred on `inj-subject-line`. The operator decides whether that card triggers the rule,
  or changes the rule.
- **More data** (item 3 decided, operator 2026-10-14; items 1 and 2 proposed):
  1. Haiku 5.5 and Sonnet 5.5 as `actor_high` on the 300-card set, two runs each, compared with
     the B0 pair (`e11c92a3`, `845303ba`; Opus `actor_high`): gives Opus a second run and Sonnet a
     preset C result.
  2. An actor-only comparison on frozen classifications, so classifier variation doesn't change
     rules between arms (6b had this from Gemma through preset B, removed in v3.0.0; whether the
     eval can freeze C classifications is unverified, and D's source query may provide it, decided
     here in v3.0.1, operator decision 2026-10-14).
  3. **Decided (operator 2026-10-14): runs in v3.0.1, not before v3.0.0.** H5, the per-role
     `actor` comparison: Haiku 5.5 as `actor` against the pinned Sonnet, two C runs on the
     300-card set against the B0 pair (`e11c92a3`, `845303ba`), using S1's known-sender cards
     (17 of 66 act claims per run go to `actor`). **Needed before the run** (operator decision
     2026-10-14): `--actor-model` sets both actor roles, `actor` and `actor_high`
     (`claude_eval.py:239`), so as built H5 can't vary `actor` alone; the plan adds a per-role
     override (e.g. one flag per role) or states a workaround before H5 runs.
- **Actor guidance** for the two cards no model got right, measured with the pin (a prompt change
  is a gate-key change too).
- Narrowing high-risk routing (first-time sender alone sends every item to `actor_high`; SPEC
  §21.2, 6b): with or after the pin.
- Version: a pin change is neither a fix nor a feature under SPEC §1.4's semver wording; the
  operator named it v3.0.1.
